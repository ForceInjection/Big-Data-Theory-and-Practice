本文档根据课程复习提纲整理，针对各章节思考题提供参考解答，旨在帮助理解核心考点与设计原理。

## 1. 大数据综述与发展脉络

### 1.1 如果一个业务每天产生 TB 级日志，要求 T+1 产出统计报表：你会如何用 “4V” 解释其系统选型倾向？

答题要点：

- **Volume (数据量大)**：每天 TB 级增量，单机无法存储和处理，必须选择**分布式存储系统**（如 HDFS）和支持**水平扩展**的计算框架。
- **Velocity (处理速度)**：要求 "T+1"（即第二天产出），属于**离线批处理**场景，对实时性要求不高（非毫秒级），侧重**高吞吐量**，适合选用 MapReduce 或 Spark 每天定时调度。
- **Variety (数据多样性)**：日志通常为半结构化（Text/JSON），需要灵活的解析能力，适合**Schema-on-Read**（读时模式）的处理方式，如 Hive 或 Spark SQL。
- **Value (价值密度低)**：海量日志中只有少量关键指标（如 PV/UV、错误率）有价值，需要通过 ETL 清洗和聚合计算“提纯”数据。

### 1.2 在 “存储 / 计算 / 服务” 三类能力中，分别举一个你认为最关键的设计目标，并说明原因

答题要点：

- **存储 (GFS/HDFS)**：**容错性**（Fault Tolerance）。
  - **原因**：构建在廉价商用硬件上，硬件故障是常态。必须通过多副本机制保证数据不丢失、服务不中断。
- **计算 (MapReduce/Spark)**：**扩展性**（Scalability）或 **移动计算**（Data Locality）。
  - **原因**：计算逻辑必须能够并行化分发到成百上千个节点；且应“移动计算到数据所在节点”以减少网络带宽消耗。
- **服务 (BigTable/HBase)**：**随机读写性能**（High Throughput Random Access）。
  - **原因**：在线服务要求低延迟响应，需要高效的索引结构（如 LSM-Tree）来支持海量数据下的快速 Key-Value 查询。

### 1.3 设想要保证同一类用户行为事件按时间顺序处理：你会优先从数据建模（字段与 key）、还是从系统组件（存储/计算）入手？为什么？

答题要点：

- **优先入手**：**数据建模（Key 的设计）**。
- **原因**：分布式系统（如 Kafka、MapReduce）通常只保证**局部有序**（Partition 内部有序）。
  - 要保证同一用户行为有序，必须在**生产端**或**Shuffle 阶段**，将该用户的 ID 作为 **Partition Key**（或 Sharding Key），确保该用户的消息被路由到同一个分区/节点处理。
  - 单纯依赖系统组件配置（如设置全局单分区）会严重牺牲吞吐量，不可扩展。

### 1.4 为什么说 Value（价值密度低）会倒逼系统强调 “批处理 + 统计建模”？结合一个你熟悉的场景说明

答题要点：

- **原因**：单条数据本身价值极低（如一条 Web 访问日志），只有汇聚海量数据进行统计分析（如趋势图、用户画像）才能发现规律。
- **场景**：电商点击流日志。单独看某用户点击了某商品意义不大，但批量分析数亿条点击日志，计算出“点击转化率”或训练推荐算法模型，才能产生商业价值。这需要大规模批处理能力来全量扫描数据。

## 2. 分布式协调与一致性基础

### 2.1 如果把 ZooKeeper 当作业务主数据存储，会遇到哪些性能与可用性风险？

答题要点：

- **数据量风险**：ZK 将所有数据加载在**内存**中，且为了性能通常限制 ZNode 大小（默认 1MB）。存储大量业务数据会导致 Full GC 频繁，甚至 OOM。
- **写入频率风险**：ZK 的写操作需要**全局强一致性**（Leader 提案 -> 多数派 Follower 确认），写性能随节点数增加而下降，无法支撑高频业务写入（如日志流）。
- **Watch 风暴**：如果大量客户端监听同一个 ZNode，一旦该节点变更，Leader 需向所有客户端发送通知，瞬间消耗大量网络带宽和 CPU，导致集群不稳定。

### 2.2 设计一个简单的分布式锁：你会选用哪种 ZNode 组合？如何处理锁抢占、超时与公平性？

答题要点：

- **ZNode 组合**：**临时顺序节点**（Ephemeral Sequential）。
- **锁抢占**：客户端在指定父节点下创建临时顺序节点，序号最小的节点获得锁。
- **超时处理**：利用临时节点的特性，客户端会话断开时节点自动删除，避免死锁。
- **公平性**：基于顺序节点的 FIFO 特性，确保先到先得的公平锁获取。
- **锁释放**：获得锁的客户端完成任务后，主动删除自己的节点，通知下一个节点获取锁。
- **公平性**：客户端判断自己创建的节点序号是否是**当前最小**的。如果是，获得锁；如果不是，监听（Watch）**比自己序号小 1** 的那个节点（实现排队，避免惊群效应）。
- **超时/异常处理**：利用**临时节点**特性。如果客户端宕机或网络断开，Session 超时，临时节点自动删除，锁自动释放，避免死锁。

### 2.3 为什么多数派机制要求集群规模通常取奇数？

答题要点：

- **容错能力**：$N$ 台机器的集群容忍 $f$ 台故障，需满足 $N > 2f$。
  - 3 台（容忍 1 台）和 4 台（容忍 1 台）的容错能力一样，但 4 台更浪费资源。
- **防止脑裂**：奇数节点更容易在网络分区时形成唯一的多数派（Majority），避免选出两个 Leader。

### 2.4 在配置中心场景里，Watch 是一次性触发的：客户端如何保证 “收到变更后一定能读到最新配置”？

答题要点：

- **机制**：**先注册 Watch，再读取数据**（或标准模式：`getData` 并在回调中再次 `getData` 并注册 Watch）。
- **关键点**：客户端收到 Watch 事件通知后，必须**主动拉取最新数据**，并**同时重新注册 Watch**。
- **边界处理**：在“收到通知”到“重新注册”的间隙如果发生了新的变更，ZK 不会发送通知，但客户端下一次读取时会读到最新版本（可能跳过中间版本，但最终一致）。

## 3. HDFS 基础机制与读写路径

### 3.1 为什么 HDFS 不适合存储数十亿个 KB 级别的小文件？

答题要点：

- **NameNode 内存瓶颈**：HDFS 元数据（文件、目录、Block 信息）全量保存在 NameNode 内存中。每个文件/Block 对象约占 150 字节。数十亿小文件会直接撑爆内存，限制集群扩展。
- **寻址开销**：读取大量小文件需要频繁与 NameNode 交互获取位置，且 DataNode 随机 IO 增多，导致寻址时间远大于数据传输时间，吞吐量极低。

### 3.2 默认 Block 大小设置为 128 MiB（甚至更大）而不是 4 KB，背后的核心权衡是什么？

答题要点：

- **权衡**：**最小化寻址开销**（Seek Time）占比，最大化**数据传输**（Transfer Time）效率。
- **目标**：让磁盘寻址时间仅占传输时间的 1% 左右。如果 Block 太小，磁头频繁寻道；如果 Block 太大，MapReduce 任务并行度可能受限（Map 任务数少）。

### 3.3 在写入 Pipeline 中，如果中间某个 DataNode 挂了，HDFS 会如何处理？

答题要点：

1. **Pipeline 断开**：客户端收到异常。
2. **建立新 Pipeline**：将挂掉的 DataNode 剔除，剩下的 DataNode 组成新的 Pipeline。
3. **继续写入**：客户端将数据包写入剩余的节点（并更新 NameNode 上的元数据版本号）。
4. **事后补全**：文件关闭后，NameNode 检测到该 Block 副本数不足（如由 3 变 2），会异步触发复制任务恢复副本数。

## 4. HDFS 高可用（HA）与扩展能力

### 4.1 为什么 HDFS HA 中需要 JournalNode 集群而不是简单的 NFS 共享存储？

答题要点：

- **脑裂保护**：NFS 容易因网络延迟或分区导致“假死”，可能出现双 Active 同时写入 NFS 破坏元数据。
- **一致性保障**：JournalNode 基于 **Paxos/Raft 类一致性协议**，必须**多数派写入成功**才算提交。即使部分 JN 挂掉，只要多数派存活，就能保证 EditLog 不丢失且一致，从根本上防止脑裂。

### 4.2 如果 ZKFC 进程挂了但 NameNode 进程正常，会发生什么？

答题要点：

- **后果**：ZKFC 负责维持 ZK Session 和锁。ZKFC 挂掉 -> ZK Session 断开 -> 临时锁节点消失。
- **切换**：Standby 的 ZKFC 监测到锁释放，会认为 Active 挂了，触发选主并尝试切换。
- **Fencing**：Standby 试图切换为 Active 前，会调用脚本（Fencing）强制 Kill 掉旧 Active 的 NameNode 进程（即使它还活着），以防止双 Active。
- **总结**：会触发一次**主备切换**，服务会有短暂抖动，但能自动恢复。

## 5. MapReduce 编程模型与 Shuffle

### 5.1 为什么 Shuffle 被称为 MapReduce 的“心脏”，同时也是性能瓶颈所在？

答题要点：

- **心脏**：Shuffle 负责连接 Map 和 Reduce，实现了数据的**全排序**（Total Sort）和**分组**（Grouping），是分布式聚合的核心逻辑。
- **瓶颈**：
  - **磁盘 I/O**：Map 端大量的 Spill（溢写）和 Merge（归并）读写磁盘。
  - **网络 I/O**：海量中间数据需跨节点传输（Copy 阶段），消耗集群带宽。
  - **CPU**：序列化/反序列化和排序操作消耗大量 CPU。

### 5.2 如果 MapReduce 任务出现数据倾斜，可能的原因是什么？如何利用 Partitioner 解决？

答题要点：

- **原因**：Key 分布不均（如某些 Key 出现频率极高），导致某几个 Reduce 处理的数据量远超其他 Reduce，拖慢整体进度（木桶效应）。
- **Partitioner 解决**：
  - **自定义 Partitioner**：修改哈希策略，将热点 Key 进一步打散（例如加随机前缀/后缀），分发到不同 Reduce。
  - **两阶段聚合**：先用随机分区做局部聚合（Local Aggregation），再去掉随机前缀做全局聚合。

## 6. YARN 资源管理与调度

### 6.1 为什么说 YARN 的架构比 MRv1 的 JobTracker 更具扩展性？

答题要点：

- **解耦**：MRv1 中 JobTracker 既管资源又管任务调度，是严重单点瓶颈。YARN 将其拆分为 **ResourceManager**（只管资源，轻量）和 **ApplicationMaster**（只管单个任务，分散在各个节点）。
- **通用性**：ApplicationMaster 是应用级别的，不同应用（MapReduce, Spark, Flink）可以实现自己的 AM，使得 YARN 成为通用资源底座。

### 6.2 如果一个 MapReduce 任务的 ApplicationMaster 挂了，整个任务会失败吗？YARN 是如何处理的？

答题要点：

- **不会立即失败**。
- **处理流程**：ResourceManager 检测到 AM 失败（心跳超时），会在另一个 NodeManager 上**重启一个新的 AM**。
- **状态恢复**：新的 AM 启动后，读取之前的作业状态（如果开启了 Log Aggregation 或作业恢复功能），可以保留已完成的 Task 结果，只需重跑未完成的任务。如果重试次数超过阈值（默认 2 次），任务才会最终失败。

### 6.3 YARN 支持哪些主要的调度算法？它们各自适用于什么场景？

答题要点：

- **FIFO 调度器**（先进先出）：

  - **适用场景**：单租户环境、简单的批处理工作负载、作业执行顺序确定且资源需求可预测的场景
  - **特点**：实现简单，但大型作业会阻塞整个队列，不适合多租户环境

- **容量调度器**（Capacity Scheduler）：

  - **适用场景**：企业级多租户环境，需要严格的资源隔离和预算控制
  - **特点**：基于层次化队列结构和预配置资源配额，支持弹性资源共享和严格的资源隔离

- **公平调度器**（Fair Scheduler）：
  - **适用场景**：多租户共享环境，需要动态公平分配和自适应调整
  - **特点**：基于实时计算的公平份额，支持智能抢占和动态资源调整

### 6.4 容量调度器和公平调度器在企业级环境中的主要区别是什么？

答题要点：

- **资源分配方式**：

  - 容量调度器：基于**预配置的队列容量**和静态配额
  - 公平调度器：基于**实时计算的公平份额**和动态调整

- **管理复杂度**：

  - 容量调度器：需要精心设计队列结构，配置相对复杂
  - 公平调度器：配置相对简单，自适应能力强

- **适用场景**：

  - 容量调度器：适合需要**严格资源隔离**和预算控制的企业环境
  - 公平调度器：适合需要**灵活资源共享**和公平性的学术研究、开发测试环境

- **弹性机制**：
  - 容量调度器：支持队列间的**弹性资源共享**（空闲资源借用）
  - 公平调度器：支持**智能抢占机制**（从超额使用的队列回收资源）

## 7. Spark 核心抽象与执行机制

### 7.1 为什么 Spark 比 MapReduce 快？

答题要点：

- **内存计算**：Spark 优先将中间结果缓存在内存（RDD Cache），避免了 MR 频繁读写磁盘（Shuffle 除外）。
- **DAG 优化**：Spark 构建 DAG（有向无环图），基于 Stage 划分进行流水线执行，优化了调度逻辑。
- **线程级 Task**：Spark Executor 是多线程模型，Task 启动开销小；MR 是进程级模型（TaskTracker 启动 JVM），开销大。

### 7.2 宽依赖和窄依赖在容错恢复时有什么区别？为什么宽依赖通常需要 Checkpoint？

答题要点：

- **窄依赖**（One-to-One）：父 RDD 的分区只被一个子 RDD 使用。恢复时只需**重算丢失的那一个分区**，开销小。
- **宽依赖**（Shuffle）：父 RDD 的分区被多个子 RDD 使用。如果子 RDD 分区丢失，需重算所有父 RDD 分区（因为数据混在一起），会导致**级联重算**。
- **Checkpoint**：为了避免宽依赖长链路的级联重算，通常在宽依赖边界将中间数据持久化到 HDFS（Checkpoint），切断依赖链（Lineage Cut）。

## 8. Hive 数据仓库与表设计

### 8.1 如果一个表的数据量很大，但查询时很少用到过滤条件，还有必要做分区吗？为什么？

答题要点：

- **没必要**（或者说收益极低）。
- **原因**：分区的核心作用是**分区裁剪**（Partition Pruning），即跳过不需要扫描的目录。如果查询通常是全表扫描（Full Table Scan），分区不仅不能加速，反而因为产生大量小目录/小文件增加 NameNode 负担和寻址开销。

### 8.2 为什么 `LOAD DATA` 命令不能保证分桶表的存储约束？

答题要点：

- **机制差异**：`LOAD DATA` 本质是 HDFS 的文件**移动/重命名**操作，不经过 MapReduce 计算。
- **分桶约束**：分桶表要求数据按 `Hash(Key) % Buckets` 严格分布在不同文件中。直接 Load 文件无法保证其中的数据满足该哈希分布，会导致查询结果错误（如 SMB Join 结果错误）。
- **正确做法**：先 Load 到临时表，再用 `INSERT INTO ... SELECT ...`（触发 MR Shuffle）写入分桶表。

## 9. HBase 列族存储模型与系统架构

### 9.1 为什么 HBase 适合写多读少的场景？

答题要点：

- **LSM-Tree 机制**：HBase 基于 Log-Structured Merge Tree。
- **顺序写**：所有的写入（Insert/Update/Delete）在内存（MemStore）中排序后，Flush 为磁盘文件（HFile）。这是一种**顺序写 I/O**，性能极高。
- **读代价**：读取时可能需要合并查询 MemStore 和多个 HFile，虽然有 BloomFilter 和 BlockCache 优化，但读路径比写路径复杂。

### 9.2 HBase 中 HMaster 挂掉会对集群有什么影响？读写请求是否立刻中断？

答题要点：

- **读写不中断**：客户端直接连接 ZooKeeper 获取 Meta 表位置，再连接 RegionServer 进行读写。HMaster 不参与数据路径。
- **管理功能失效**：无法创建/删除表，无法进行 Region 的负载均衡和分裂/合并（Split/Compact）调度，无法处理 RegionServer 的故障转移。长期来看集群会失衡或不可用。

### 9.3 简述 Major Compaction 和 Minor Compaction 的区别及对业务的影响

答题要点：

- **Minor Compaction**：合并少量相邻小 HFile，不处理删除标记（Tombstone），开销较小。
- **Major Compaction**：合并 Region 下所有 HFile 为一个大文件，**物理删除**过期和标记删除的数据。
  - **影响**：消耗大量磁盘 I/O 和网络带宽，可能导致 RegionServer 响应变慢甚至 Full GC。通常建议在业务低峰期手动触发。

## 10. Kafka 分布式消息队列与分区有序性

### 10.1 如果要求所有消息全局有序，Kafka 应该如何配置？

答题要点：

- **配置**：Topic 只能设置 **1 个 Partition**。
- **代价**：彻底牺牲并行度和吞吐量，退化为单机队列性能。

### 10.2 Kafka 为什么读写吞吐量高？

答题要点：

- **顺序写磁盘**：Partition 是追加日志（Append-only），利用磁盘顺序 I/O 性能。
- **零拷贝（Zero-Copy）**：利用 `sendfile` 系统调用，数据直接从 PageCache 传输到网卡，避免内核态与用户态的多次拷贝。
- **PageCache**：利用操作系统文件缓存，尽量在内存中操作数据，减少磁盘物理读写。

### 10.3 Consumer Group 中 Consumer 的数量超过 Partition 数量会有什么后果？

答题要点：

- **后果**：**多余的 Consumer 会空闲（Idle）**，无法消费任何数据。
- **原理**：Kafka 保证一个 Partition 在同一时刻只能被组内的一个 Consumer 消费（为了保证局部有序性）。并行度上限是 Partition 数。

## 11. 数据采集与流处理基础

### 11.1 简述 Flume 中 Memory Channel 和 File Channel 的适用场景

答题要点：

- **Memory Channel**：基于内存队列。
  - **场景**：极高吞吐量，允许因断电/宕机丢失少量数据（如非核心日志）。
- **File Channel**：基于磁盘 WAL。
  - **场景**：金融/计费等**数据零丢失**场景，可靠性要求高，吞吐量相对较低。

### 11.2 什么是"背压"（Backpressure）？流处理系统中如何处理背压？

答题要点：

- **定义**：下游消费速度跟不上上游生产速度，导致数据堆积。
- **处理**：
  - **Flink**：基于**网络流控机制**。当下游处理能力不足时，通过 TCP 层的流量控制机制自动减缓上游数据发送速率，压力逐级反向传递到 Source 端，实现系统自调节。
  - **Spark Streaming**：基于**微批处理模型**。通过监控批次处理时间，动态调整下一批次拉取的记录数，使用 PID 控制器进行速率限制。

### 11.3 Spark Streaming 的微批模式相比 Flink 的事件驱动模式，有什么优缺点？

答题要点：

- **Spark Streaming (Micro-batch)**：
  - **优点**：吞吐量高，基于 RDD 生态成熟，容错简单（小任务重算）。
  - **缺点**：延迟较高（秒级），很难处理乱序时间（Event Time）和复杂的 Session Window。
- **Flink (Native Streaming)**：
  - **优点**：低延迟（毫秒级），原生支持 Event Time、Watermark 和高级窗口，State 管理强大（Exactly-Once）。
  - **缺点**：架构复杂，调优门槛较高。

## 12. 数仓、数据集市与数据湖

### 12.1 为什么说“不加治理的数据湖就是数据沼泽”？

答题要点：

- **原因**：数据湖接收原始数据（Raw Data），如果没有元数据管理（Catalog）、数据质量监控、权限控制和生命周期管理，数据湖就会变成一个**不可知、不可用、不安全**的文件垃圾堆，无法产生业务价值。

### 12.2 对比 Schema-on-Write 和 Schema-on-Read 的优缺点

答题要点：

- **Schema-on-Write（写时模式 - 数仓）**：
  - **优点**：读取速度快（预处理过），数据质量高。
  - **缺点**：写入灵活性差，Schema 变更困难。
- **Schema-on-Read（读时模式 - 数据湖）**：
  - **优点**：写入极快（直接存），灵活性高（适应多变结构）。
  - **缺点**：读取时需解析，性能较差，易出错。

### 12.3 简述数仓分层（ODS/DWD/DWS/ADS）的作用和每一层的主要职责

答题要点：

- **ODS (Operational Data Store)**：**贴源层**。保持与源系统数据一致，仅做基础备份，不做复杂处理。**关键特征**：无损快照，保留原始字段名和编码。
- **DWD (Data Warehouse Detail)**：**明细层**。进行清洗（去重、脱敏）、规范化（维度退化、数据字典映射），保持明细粒度。**关键特征**：统一口径，消除源系统差异。
- **DWS (Data Warehouse Service)**：**汇总层**。按主题进行轻度或高度聚合（如按天统计 UV），为上层提供公共指标。**关键特征**：面向主题，沉淀公共指标。
- **ADS (Application Data Service)**：**应用层**。面向具体业务报表，存储最终结果数据（通常存入 MySQL/Redis）。**关键特征**：按需定制，隐藏复杂加工过程。
