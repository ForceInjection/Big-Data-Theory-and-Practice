# 第 12 章《从数据仓库到湖仓一体》教学设计与作业

本文件面向授课教师与助教，配合 `courses/chapter12/从数据仓库到数据湖.md` 使用，给出本章的课堂讲授提纲、课堂讨论题以及课后作业设计方案，适用于研究生一年级课程。

---

## 一、课堂讲授提纲（建议 3 学时）

### 1. 第 1 学时：从银行案例到三代数据架构

**教学目标**：

1. 通过同一银行跨行对账业务的演进，直观理解从 Data Warehouse 到 Data Lake，再到 Lakehouse 的驱动力。
2. 建立对数仓分层（ODS/DWD/DWS/ADS）和数据湖基本形态的整体认知。
3. 初步理解 Table Format 在三代架构中的位置。

**时间与内容安排（约 90 分钟）**：

- 0–10 分钟：课程定位与前情回顾

  - 回顾前续章节（HDFS、MapReduce/Spark、Hive、Parquet、流式计算等）。
  - 引出核心问题：“整体数据架构应该长成什么样，以及为什么会这样长”。

- 10–35 分钟：第 1 章 1.1–1.2（数据仓库 → 数据湖）

  - 1.1 传统银行 T+1 对账与监管报表：
    - 数据来源：核心系统、渠道系统、清算机构、基础数据系统。
    - 数仓 ODS/DWD/DWS/ADS 分层流水线及各层职责。
    - 数仓在统一口径、稳定报表、问题追溯方面的优势。
  - 1.2 银行数据湖案例：
    - 数据湖建设目标：多类型数据、低成本长期存储、探索性分析。
    - 目录结构示意（raw/clean/feature/warehouse）及各层定位。
    - “数据沼泽”问题：元数据混乱、无事务、一堆小文件、合规删除困难。

- 35–55 分钟：第 1 章 1.3（湖仓一体的动机与整体架构）

  - 三类新诉求：实时风控、运营看板、合规追溯。
  - 湖仓一体端到端链路示意：核心交易数据库 → Flink CDC → Iceberg/Hudi 表 → Spark/Trino 等。
  - 三阶段性能与成本对比表：从“成本—效率—质量”三维度理解演进。

- 55–75 分钟：第 2 章（抽象出三代数据架构共性）

  - 2.1 第一代数据仓库：
    - 电商离线数仓案例与星型/雪花模型示意。
    - Schema-on-Write、T+1 批处理、统一数据口径的优点与局限。
  - 2.2 第二代数据湖：
    - Schema-on-Read、低成本存储、“先存后用”的理念。
    - 数据湖在治理与一致性方面的内在短板。
  - 2.3 第三代 Lakehouse：
    - Data Warehouse / Data Lake / Lakehouse 对比表的关键维度讲解。

- 75–90 分钟：第 3 章（Table Format 的概念与问题清单）
  - 区分 File Format 与 Table Format 各自解决的问题。
  - 列出 Table Format 要解决的四类关键问题：元数据扩展性、MVCC、Schema 演进、统一批流写入。
  - 引导到下一学时：Iceberg 如何在工程上具体实现这些能力。

---

### 2. 第 2 学时：Iceberg 内部机制与工程细节

**教学目标**：

1. 理解 Iceberg 元数据分层结构及 Catalog 的作用。
2. 掌握 Copy-On-Write 写入路径与 ACID 语义的对应关系。
3. 理解 Time Travel、隐藏分区与 Retention/GC 在性能与合规上的意义。

**时间与内容安排（约 90 分钟）**：

- 0–10 分钟：快速回顾与概念问答

  - 简要回顾三代架构差异与 Table Format 的定位。
  - 通过 1–2 个简单问题检查学生对数据湖问题及 Lakehouse 动机的掌握情况。

- 10–35 分钟：第 4 章 4.1 元数据层设计

  - 自底向上讲解 Data File → Manifest File → Manifest List → Metadata File → Catalog。
  - 结合跨行对账结果表的 ASCII 图解释“哪些文件属于这张表”“当前快照是什么”。
  - 强调 Iceberg 如何避免依赖目录 Listing，并支撑大规模元数据管理。

- 35–65 分钟：第 4 章 4.2–4.3 读写路径与 Time Travel

  - 4.2：Copy-On-Write 写入流程的 8 个步骤，与 ACID 四要素一一对应。
  - 4.2：乐观并发控制（Optimistic Concurrency Control）及 CDC Upsert/Delete 场景。
  - 4.3：Time Travel 的基本思想：按时间点或快照 ID 查询历史状态，而不复制多份表。

- 65–85 分钟：第 4 章 4.4–4.6 性能与成本控制

  - 4.4：隐藏分区与 Data Skipping，类比 Hive 显式分区的使用方式。
  - 4.5：Retention 与垃圾回收策略，解释为何不能无限保留所有快照。
  - 4.6：将上述机制映射回银行对账案例（统一视图、近实时风控、历史追溯与合规删除）。

- 85–90 分钟：小结与提问
  - 总结 Iceberg 为数据湖叠加的“数据库式能力”。
  - 留出 1–2 个开放问题，为第三学时的生态与实践篇做铺垫。

---

### 3. 第 3 学时（可选强化）：现代数据栈与实践场景

**教学目标**：

1. 能够用分层视图描述一个现代数据平台（Modern Data Stack）。
2. 能将典型场景（CDC 入湖、流批一体、特征湖等）映射到具体组件与链路。
3. 能够从平台视角理解业界方案与未来演进趋势。

**时间与内容安排（约 90 分钟）**：

- 0–10 分钟：回顾与目标说明

  - 回顾 Iceberg 内部机制要点。
  - 说明本学时将从“组件与实践”角度看 Lakehouse。

- 10–40 分钟：第 5 章 现代数据栈全景

  - 讲解五层架构：接入层、计算层、表格式层、存储层、元数据与编排。
  - 引导学生将自己熟悉的系统或课程项目映射到该分层架构。
  - 可以选 1–2 名学生在黑板上画出映射图并全班讨论。

- 40–70 分钟：第 5 章 5.2 四个典型场景

  - 场景一：CDC 实时入湖。
  - 场景二：流批一体。
  - 场景三：历史数据修正与合规。
  - 场景四：特征湖与机器学习。
  - 以分组形式，让每组选择 1 个场景，画出 Source → Transport → Sink → Query 的端到端链路，并标出 Table Format 发挥作用的位置。

- 70–85 分钟：第 6 章 业界形态与未来展望

  - 6.1：商业平台、云厂商方案、开源自建方案三类形态及共性思路。
  - 6.2：从“成本—效率—质量”三维度再次回顾三代数据架构演进。
  - 结合本章末尾的思考题引导学生进行简短讨论。

- 85–90 分钟：推荐阅读说明与作业布置
  - 说明“推荐阅读与扩展资料”小节中的关键条目。
  - 简要介绍课后作业要求及评估要点。

## 二、课堂讨论题设计（按章节/小节组织）

以下讨论题可根据课程时长与教学风格在课堂中选用，每个问题建议预留 5–10 分钟讨论时间。

### 1. 第 1 章：银行案例与业务驱动力

1. 在只有 T+1 数据仓库的阶段，如果不引入数据湖，你会如何缓解“日志太多放不下”“新数据源接不进来”的问题？这些做法的长期代价是什么？
2. 在银行案例中，数据湖解决了哪些数仓难以解决的问题？又带来了哪些新的治理压力？
3. 在同一个银行场景中，Lakehouse 带来的最大“增量价值”是什么？你更看重实时性、合规性还是成本？请说明理由。

### 2. 第 2 章：三代数据架构抽象

1. 对比传统 MPP 数仓与 Hive 数仓，它们在成本结构、扩展性和运维复杂度上的差异是什么？为什么很多企业仍然保留 MPP 数仓？
2. 数据湖中的“数据沼泽”问题，哪些更偏技术原因，哪些更多来自组织结构与流程？如果你负责数据治理，会优先解决哪一类问题？
3. 在“数仓 + 实时链路”和“Lakehouse 一套系统”之间，你认为哪些业务场景仍然适合保留前一种架构？哪些场景更适合向 Lakehouse 演进？

### 3. 第 3–4 章：Table Format 与 Iceberg 机制

1. 单靠 Hive Metastore + Parquet 文件，为什么难以优雅地支持 Time Travel 和行级删除？请结合“目录即元数据”的局限分析。
2. Iceberg 采用 Copy-On-Write（写新文件 + 切换快照指针）而不是“就地更新”的主要原因是什么？还有哪些替代方案？优缺点分别是什么？
3. 在 Time Travel 与 Retention 的权衡中，你会如何设置快照保留窗口？请从存储成本、性能与合规审计三个角度给出理由。

### 4. 第 5–6 章：现代数据栈与业界形态

1. 在现代数据栈中，如果去掉“表格式层”，只保留对象存储 + 计算引擎，系统会在一致性和治理上面临哪些复杂度？
2. 对比“全托管平台”和“基于开源组件自建方案”，对于一家中型互联网公司，你会如何选择？请给出 2–3 个关键决策维度并说明理由。
3. 未来 5 年内，你认为 Lakehouse 与流式数据平台（Kafka/Flink）在架构上可能如何融合？是“流为主、湖为辅”，还是相反？请结合本章内容进行推理。

## 三、课后作业设计（与章节内容对应）

### 作业一：三代架构对比分析报告（对应第 1–2 章）

**作业目标**：

1. 加深对 Data Warehouse / Data Lake / Lakehouse 三代架构差异的理解。
2. 能够将课堂中的抽象概念应用到具体业务场景分析中。

**作业内容**：

选择一家你熟悉的企业或虚构一个业务场景（例如电商、银行、风控、广告平台），完成以下任务：

1. 描述该企业在第一代数据仓库阶段可能采用的架构：
   - 涉及的核心组件（OLTP 数据库、ETL 工具、数仓集群、报表/BI 系统等）；
   - 典型数据流与主要报表。
2. 说明引入数据湖后解决了哪些问题（数据类型、多源接入、存储成本等），同时产生了哪些新的复杂度（元数据治理、小文件、合规删除等）。
3. 设计一套基于 Lakehouse 的目标架构，用简图说明关键组件和数据流，并解释：
   - Lakehouse 如何在不放弃数据湖低成本优势的前提下补齐事务与治理能力；
   - 对比前两代架构，在成本、效率、质量三方面的改善。

**作业要求**：

- 报告长度建议为 2–3 页，包含 1–2 张架构示意图。
- 建议参考教案第 1、2 章以及推荐阅读列表中的相关条目（例如关于传统数据仓库与数据湖的资料）。

---

### 作业二：Table Format 机制精读小结（对应第 3–4 章）

**作业目标**：

1. 通过精读原始论文或官方文档，深入理解 Table Format 的设计初衷与关键机制。
2. 能够将 Iceberg/Hudi/Delta Lake 等系统与本章抽象框架进行对照。

**作业内容**：

从推荐阅读与扩展资料中选择一项与 Table Format 直接相关的资料（例如 Delta Lake 论文、Iceberg 规范、Hudi 官方文档），完成以下任务：

1. 用自己的话总结该 Table Format 主要解决的三个问题，并分别对应到本教案第 3–4 章中的相关内容。
2. 画出其元数据管理的简化结构图（可参考教案中的 Iceberg 元数据层级图），标注关键概念及其关系。
3. 选择一个具体应用场景（可以继续使用银行跨行对账案例，也可以自选业务），说明：
   - Time Travel 在该场景中的使用方式和价值；
   - Upsert/Delete 语义在该场景中如何支撑合规要求或数据修正需求。

**作业要求**：

- 文字部分建议约 1500 字。
- 图示可以手绘扫描或使用制图工具绘制。
- 建议在报告中明确标出参考的文献或文档编号（对应推荐阅读列表）。

---

### 作业三：现代数据栈架构设计与方案说明（对应第 5–6 章）

**作业目标**：

1. 训练学生从“整个平台”视角设计数据架构的能力。
2. 促使学生将课程中学习的组件（HDFS、Spark、Flink、Table Format 等）整合到一个统一方案中。

**作业内容**：

以“为某个业务团队设计一套现代数据平台”为目标，完成以下任务：

1. 按照第 5 章的五层架构（接入层、计算层、表格式层、存储层、元数据与编排），为每一层选择 1–2 个代表性组件，可以混合使用云服务与开源软件，并简要说明选择理由。
2. 从第 5 章的四个典型场景中选择一个（CDC 实时入湖、流批一体、历史修正与合规、特征湖与机器学习），画出该场景下的端到端数据链路：
   - 明确 Source、Transport、Sink、Query 所对应的组件；
   - 标注关键数据表或 Topic 以及数据流向。
3. 分析在该方案下：
   - 哪些能力由 Table Format 提供（例如 ACID 事务、Time Travel、隐藏分区、Data Skipping 等）；
   - 哪些能力依赖于计算引擎（Spark/Flink/Trino 等）或编排系统（Airflow/DolphinScheduler 等）。

**作业要求**：

- 报告长度建议为 3–4 页，至少包含一张完整的架构图。
- 在组件选择上，鼓励尝试将 Iceberg/Hudi/Delta Lake/Apache Paimon 等作为表格式层候选，将 StarRocks/Apache Doris 等作为 MPP/HTAP 引擎候选，并结合推荐阅读中的官方文档思考它们在整体架构中的定位。
- 鼓励学生参考推荐阅读中的平台或白皮书（例如 Databricks Lakehouse、云厂商湖仓一体方案等），并在文中指出参考来源。
- 评分时可重点考察：架构是否自洽、组件选择是否合理、Table Format 角色是否被清晰识别。
