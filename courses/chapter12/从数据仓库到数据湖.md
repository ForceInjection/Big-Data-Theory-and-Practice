# 从数据仓库到湖仓一体：现代数据架构的演进与原理

本课程聚焦从传统数据仓库到数据湖、再到湖仓一体（Lakehouse）的演进路径，强调**原理讲解与架构思维训练**，帮助学习者从工程实践和系统设计两个维度理解现代数据平台的整体图景。

本节课程与前续章节（HDFS 文件系统、MapReduce/Spark 计算、Hive 数仓、Parquet 列存、ETL 与流式计算等）形成闭环：前面的课程回答“如何存、如何算、如何流”，本课程回答“整体架构应该长成什么样，以及为什么会这样长”。

通过本课程的学习，读者将能够：

1. 系统回顾从传统数据仓库到数据湖、再到湖仓一体的**演进脉络与驱动力**。
2. 理解数据湖常见问题（数据沼泽、元数据失控）的**根源与工程症状**。
3. 掌握 Lakehouse 的核心技术基石——**Table Format（表格式）** 的设计思想与实现原理。
4. 建立现代数据栈中存储、计算、格式、编排等组件之间的**角色分工与协同关系**。
5. 能够基于典型业务场景，对比分析 Data Warehouse / Data Lake / Lakehouse 的**架构优劣与适用边界**。

建议教学时长：2 ～ 3 学时，可安排为：

- 第 1 学时：数据架构演进 + 数据湖问题分析；
- 第 2 学时：Table Format 原理 + Lakehouse 内部机制；
- 第 3 学时（可选）：结合企业案例的架构设计讨论与课堂练习。

## 第 1 章 典型应用案例：银行从数据仓库到湖仓一体的演进

本章在流计算“跨行转账对账”案例的基础上，沿着同一组业务场景，依次走过**数据仓库 - 数据湖 - 湖仓一体**三个阶段。通过对“同一家商业银行同一类业务”的持续追踪，读者可以更直观地看到：架构并不是凭空设计出来的，而是被业务需求和成本压力一点一点“推”出来的。

在后续章节中，凡是提到“数据仓库”，都可以先粗略地理解为：**围绕分析和决策场景构建的、以主题为中心的历史数据集合，用统一口径为报表和分析服务，而不是面向在线交易的业务数据库**。

从业务演进与技术演进的双重视角来看，本章重点围绕三个问题展开：

1. 在只有 T+1 数据仓库时，**哪些监管报表 / 历史分析类诉求已经被很好满足，哪些实时风控 / 数据科学类诉求开始显得吃力**？
2. 为了引入更多数据类型、降低长期存储成本，银行为什么会选择建设数据湖，而不是简单“再堆一套数仓”或“继续扩容现有数仓”？
3. 当数据湖逐渐“沼泽化”之后，银行为什么又不得不在其之上重建类似数据库的管理能力，走向 Lakehouse，用一套架构同时支撑批处理与流式更新？

围绕上述三个问题，本章的学习目标可以概括为：

1. 从具体银行业务出发，清晰界定传统 T+1 数据仓库“擅长解决什么、不擅长解决什么”，理解其价值与边界；
2. 理解引入数据湖后在数据类型与成本上的收益，以及“数据沼泽”的真实表现和成因；
3. 理解银行为何最终走向 Lakehouse 架构，并能够用自己的话解释其在风控、运营与合规上的优势；
4. 将“技术选型”背后的业务驱动力和长期运维成本看得更清楚，能够用本章的三大问题作为复盘框架，而不仅仅停留在名词层面。

### 1.1 传统银行数据仓库案例：T+1 对账与监管报表

在介绍流数据时，我们已经从 ETL 角度分析了“跨行转账对账”的端到端链路：从核心交易系统、渠道系统、外部支付机构到对账处理数据库和数据仓库。我们现在从“数据仓库”的角度重新审视这一场景。

#### 1.1.1 数据来源与抽取视角回顾

银行日终批处理场景中，典型的数据来源包括：

- **核心交易系统**：存储所有跨行转账交易明细，通常使用 Oracle / DB2；
- **渠道系统**：网银、手机银行、ATM 等多渠道的交易发起记录；
- **清算机构系统**：银联、网联、央行支付系统输出的对账文件；
- **基础数据系统**：客户信息、账户信息、费率规则、组织机构等。

在传统数仓架构下，这些数据通常通过 ETL 流程抽取到数仓 ODS 层（可以是 Greenplum、Teradata，也可以是 Hive 数仓），形成统一的对账主题数据集。

```sql
-- 提示：对账结果事实表（数仓层教学示例，基于第 11 章延伸）
CREATE TABLE dw_fact_reconciliation (
    batch_date       DATE,             -- 对账批次日期
    channel          VARCHAR(20),      -- 交易渠道（柜面、网银、手机银行等）
    internal_count   INT,              -- 内部交易笔数
    external_count   INT,              -- 外部对账笔数
    internal_amount  DECIMAL(18,2),    -- 内部交易总金额
    external_amount  DECIMAL(18,2),    -- 外部对账总金额
    diff_count       INT,              -- 差异笔数
    diff_amount      DECIMAL(18,2),    -- 差异金额
    recon_status     VARCHAR(10),      -- 对账状态：balanced / unbalanced
    load_time        TIMESTAMP         -- 数仓加载时间
);
```

这一事实表通常会与渠道维度、交易类型维度、机构维度等关联，为监管报表和内部分析提供统一的数据基础。

#### 1.1.2 数仓分层与主题建模

在进入具体分层之前，我们先用一两句话回答“什么是数据仓库”以及“为什么它能在这一阶段解决问题”。

- 在工程实现上，数据仓库可以被看作是**围绕分析决策场景设计的一组主题数据集合**，这些数据按照统一的口径和维度组织起来，专门服务于报表、分析和决策，而不是直接服务于交易落单这类在线业务。
- 在业务价值上，它的核心作用是：**把分散在多个业务系统里的交易、账户、客户、机构等信息，用统一的口径整合到一起**，让监管部门、风控部门、经营管理层看到的是“同一套数字”，避免“每个系统都有一套自己的答案”。

在银行的对账场景里，这意味着：即便核心系统、渠道系统、清算机构系统各自有自己的库和表，经过数仓建模之后，关于“某日某渠道跨行转账是否已经对平”这样的问题，应该在整个银行内部只存在一种标准答案。

为了系统性地实现这一目标，并兼顾追溯、汇总和下游消费，银行往往按照经典的数仓分层设计对账主题：

- **ODS 层**：按天落地清洗后的对账明细，基本保持与源系统一致，用于问题追溯；
- **DWD 层**：对对账明细进行统一编码、口径对齐，增加维度外键，消除冗余；
- **DWS 层**：按渠道 / 交易类型 / 机构等维度汇总生成主题汇总表；
- **ADS 层**：为监管报表、风险管理报表、管理驾驶舱等下游应用提供宽表或指标表。

典型汇总 SQL（教学示例）：

```sql
-- 提示：从明细层汇总生成对账主题汇总表的示例
INSERT INTO dws_reconciliation_summary
SELECT
    batch_date,
    channel,
    COUNT(*)                                    AS total_trans_count,
    SUM(trans_amount)                           AS total_trans_amount,
    SUM(CASE WHEN recon_result = 'DIFF' THEN 1 ELSE 0 END) AS diff_trans_count
FROM dwd_reconciliation_detail
WHERE batch_date = DATE '2023-12-08'
GROUP BY batch_date, channel;
```

从流程关系上看，可以把 ODS / DWD / DWS / ADS 理解为一条逐步「提炼」数据的流水线：

- **ODS 层**更多关注“把各系统的数据完整、可追溯地搬进来”，是原始事实的承载点；
- **DWD 层**在 ODS 之上完成“对齐口径、打通维度”的标准化处理，是主题明细的统一入口；
- **DWS 层**在 DWD 之上面向分析场景做汇总，是“可直接回答业务问题的中间层”；
- **ADS 层**则把 DWS（以及必要时的 DWD）进一步加工成针对某一类用户（监管、风控、经营管理）的专用数据集，是真正被「看见」和「消费」的部分。

通过数仓分层，银行可以：

- 统一各系统的对账口径，并在 DWD 层固化这套统一口径；
- 为监管报送提供稳定可靠的数据来源，主要沉淀在 DWS / ADS 层；
- 同时保留 ODS 层用于问题追溯，支撑按机构、渠道、产品等维度的多维分析与历史回看。

#### 1.1.3 作业调度与运行特征

在传统数据仓库阶段，对账主题相关的数仓作业通常遵循典型的“日终集中跑批”模式：所有与跨行对账和监管报表相关的任务会被统一安排在夜间窗口执行，必须在 4 ～ 6 小时的批处理时间窗内完成；一旦某个关键作业失败，调度系统会立即触发告警和重跑机制，确保第二天清晨之前对账和报表结果可以按时产出。从业务方视角看，对这些任务的要求往往是“宁可晚一点、也不能算错一笔”，因此对数据完整性和一致性有极高要求，而对实时性则相对宽松（T+1 在绝大多数监管场景下是可以接受的）。

如果把时间维度拉长来看，这种模式的**优势与隐患是并存的**：一方面，数仓通过统一的模型和批处理流程，确保了对账口径一致、监管报表稳定、数据质量有保障，成为银行信息化建设中的“基本盘”；另一方面，一切都围绕日终批处理展开的调度方式，使得系统难以对实时风控、实时限额监控、实时欺诈检测等新型场景给出分钟级甚至秒级的支撑。

随着业务场景不断扩展，银行内部围绕数据的诉求会逐渐汇聚成三条清晰的脉络：

1. 风控和运营部门希望在**更短的时间窗口内看到关键指标**，而不是第二天再看；
2. 数据科学团队希望接入更多行为数据、日志数据，用于建模和实验，而不仅是结构化交易表；
3. IT 部门希望**控制存储和计算成本**，避免所有需求都压在昂贵的数仓资源上。

当这三类诉求叠加在一起时，“只靠现有 T+1 数仓再多堆几张表”往往只能在短期内勉强支撑，长期来看无论是成本还是复杂度都难以为继。此时，从架构演进的角度出发，银行自然会开始思考：是否需要一个能够容纳更多数据类型、在长期存储成本上更可控、对分析方式限制更少的统一底座——也就是后续将要引入的数据湖。

### 1.2 银行数据湖案例：统一存储与“数据沼泽”的风险

在上一小节中，银行已经依托传统数据仓库搭建起较为完备的 T+1 监管报表体系：日终批处理可以稳定产出对账结果和各类监管报表，管理层也有了统一、可信的“官方数字”。然而，随着业务的纵深发展和数字化程度的提升，仅依靠这套体系已经难以承载所有与数据相关的期待。

一方面，业务线和风控条线不断提出“要看”的新数据源，例如 APP 行为日志、反洗钱规则命中记录、风控规则引擎日志等，希望通过这些行为线索和规则命中记录来识别潜在风险模式；另一方面，数据科学团队也希望拥有一个更自由的“试验场”，可以随时拉取原始数据做探索性分析和建模，而不受制于既有数仓宽表的字段设计。与此同时，IT 部门还面临着一个现实的问题：随着历史交易明细和原始对账文件逐年累积，如果继续把所有数据留在成本较高的数仓或在线系统中，长期的存储开销将难以接受。

在上述多方诉求的叠加推动下，银行开始探索一种新的数据承载形态：它不直接替代现有数仓，而是作为底层统一的“数据池”，以 HDFS / 对象存储为基础，低成本地接纳更多类型、生命周期更长的数据，这便是后续要重点讨论的数据湖。

#### 1.2.1 数据湖建设目标

从架构职责的角度看，银行引入数据湖并不是为了“再造一个数仓”，而是希望在现有数仓之下增加一层更宽的“数据底座”，主要承担三类职责：

1. **统一存储更多类型的数据**：不仅存储结构化的交易表和对账结果，还可以长期保留半结构化的访问日志、规则引擎日志、模型训练数据集、外部征信数据等，为后续的多种分析和建模场景预留空间；
2. **降低长周期存储成本**：将历史交易明细、原始对账文件、审计日志等从昂贵的数仓或业务系统中迁移出来，落在以 HDFS / 对象存储为代表的低成本存储介质上，使“数据多留几年”在经济上变得可行；
3. **支撑数据科学与探索性分析**：提供面向原始数据的直接访问能力，让 Spark / Flink / Presto 等不同计算引擎可以在同一套底层数据之上进行探索分析，而不必为每一次实验都提前设计好数仓宽表。

在实践中，这些目标往往会体现在一个相对规范的目录结构和分层策略上。例如，在教学场景中可以采用如下简化示意：

```text
# 银行数据湖目录结构示意（简化版）
/bank_lake
  /raw                    # 原始层：完全保留的原始数据
    /core_sys             # 核心系统全量 / 增量快照
    /recon_files          # 银联 / 网联 / 央行原始对账文件
    /app_logs             # 手机银行 / 网银访问日志
  /clean                  # 清洗层：基本质量校验 + 轻度转换
    /recon_txn_parquet
    /app_events_parquet
  /feature                # 特征层：风控 / 反洗钱模型特征
  /warehouse              # 在湖上的数仓层（Hive 或 Lakehouse 表）
```

其中：

- `raw` 层承担“如实落地”的职责，强调完整性和可追溯性；
- `clean` 层在保留主要信息的前提下做基础清洗和格式规范化，便于下游重复使用；
- `feature` 层则偏向于面向具体模型的特征视图，是风控 / 反洗钱等团队的工作成果沉淀地；
- `warehouse` 层可以看作是“建在湖上的数仓”，既可以是 Hive 表，也可以是基于 Iceberg / Hudi 等实现的 Lakehouse 表，用于承接传统报表和指标体系。

#### 1.2.2 实际收益与问题暴露

从建设初期来看，数据湖的引入确实带来了立竿见影的收益：一方面，越来越多历史原始数据可以被以较低成本长期保留下来，“存不下、存不起”的压力得到明显缓解；另一方面，数据科学团队可以直接读取 `raw` / `clean` 层的数据进行探索分析，不再被动等待数仓建模完成之后的宽表视图；同时，引入 Spark / Flink / Presto 等多种计算引擎后，批处理、交互式分析、特征抽取等多种加工方式都可以在同一套底层数据上展开。

然而，随着时间推移和团队数量、数据源数量的不断增加，数据湖也逐渐开始暴露出一系列结构性问题：

1. **元数据与目录管理混乱**  
   在缺乏统一规范和治理的前提下，不同团队会在 `/raw`、`/clean` 等目录下各自创建子目录，采用各自的命名规则和目录层级，且文档往往不完整甚至缺失。久而久之，很难搞清楚某个下游表究竟依赖了哪些原始文件，上线新任务前需要大量沟通和排查才能确认数据含义与来源。

2. **无事务导致的一致性问题**  
   数据湖底层依托的 HDFS / 对象存储通常只提供“尽力而为”的写入语义而非完整事务保障。某些 Spark 作业在写入 Parquet 文件时，如果中途失败，可能会留下不完整的目录结构或半写入的文件；下游查询任务在进行目录 Listing 时，很可能在某个时间窗口内读到未写完的数据，导致对账报表或分析结果偶发异常，这种问题在生产环境中极难复现与排查。

3. **小文件与性能瓶颈**  
   为了满足更高更新频率的需求，越来越多实时 / 近实时作业会不断向数据湖写入小批量数据，时间一长 `/clean/recon_txn_parquet` 等目录下可能累积数十万甚至上百万个小文件。查询任务在执行前需要列举并打开大量文件，元数据服务和对象存储的压力显著上升，导致查询延迟和资源成本成倍放大。

4. **合规与数据删除困难**  
   在缺乏表级版本管理和行级删除能力的情况下，对于需要删除的敏感记录（例如用户行使“被遗忘权”）往往只能通过“重写整批文件”的方式实现，成本高昂且容易遗漏；同时，由于没有系统性的版本管理与快照机制，想要精确回溯某一天的湖中数据状态或回滚到某个历史版本几乎是不可能完成的任务。

从驱动力的角度看，“数仓 + 数据湖”阶段同样存在一组相互矛盾的现实：一方面，数据湖显著缓解了“数据放不下、存不起”的压力，也让更多日志、模型数据有了归宿；另一方面，随着数据源数量和团队数量的增加，目录结构、元数据、一致性和合规问题迅速放大，**数据湖本身开始变成新的复杂系统**。

银行在这一阶段会逐渐意识到，单靠“把数据都先放进湖里”远远不够，还必须正面回答三个问题：

1. 谁来保证写入过程的原子性和一致性，避免“半写入”的目录被下游误读？
2. 谁来管理随时间不断变化的 Schema 和版本，保证不同团队看到的数据口径一致？
3. 在合规和审计压力不断加大的前提下，如何做到“既能长期保留，又能按需追溯和删除”？

这些问题的共同指向是：**需要在数据湖之上重建类似数据库的表级管理能力**——既保留湖的低成本与开放性，又引入事务、Schema 管控和时间旅行能力，这就自然引出了下一节将要讨论的 Lakehouse 实践。

### 1.3 银行湖仓一体案例：从 T+1 到近实时风控与运营

在经历了“传统数仓 + 数据湖”并存的一段时期之后，银行会发现：虽然**数据放得下了、类型也丰富了**，但要在**同一套数据基础上同时满足监管报表、实时风控、运营看板和合规审计等多种需求**，仍然力不从心。典型的矛盾体现在三类诉求上：

1. 线上风控、反洗钱、欺诈检测等一线业务希望以**分钟级甚至秒级的频率**感知交易和对账异常，而不是在第二天的批处理结果中“事后追认”；
2. 运营团队希望**实时看到关键指标**（交易失败率、渠道可用性、风控拦截率等），并基于这些指标灵活调整运营策略和资源投放；
3. 合规与稽核团队希望对数据变更保持**可追溯性和可回滚能力**，在发现问题时能够快速回溯到某一历史状态，甚至一键回滚到上一个稳定版本。

在数仓阶段，这些诉求受限于 **T+1 批处理** 的节奏；在“数仓 + 数据湖”阶段，虽然底层数据更加丰富，但缺乏**表级事务、版本管理和统一 Schema 管控**，使得“**同时满足实时性、正确性和可追溯性**”变得非常困难。出于这些考虑，银行开始基于 Iceberg / Hudi / Delta Lake 等技术构建湖仓一体架构。

#### 1.3.1 目标与整体架构

与其把 Lakehouse 看作“第三套系统”，不如将其理解为在数据湖之上叠加的一层“**表级管理**与**计算协同能力**”。在银行场景中，其整体目标可以概括为三个方面：

1. **继承数据湖的低成本与多引擎能力**：继续依托 HDFS / 对象存储作为底层存储，让 Spark / Flink / Trino / Presto 等引擎可以共享同一套数据；
2. **补齐数据库级的事务与 Schema 管理能力**：在“只保证最终一致”的文件系统之上，引入 ACID 事务、Snapshot 与 Time Travel 等机制，回答上一小节提出的“原子性与一致性”“Schema 与版本管理”“可追溯与可删除”三个问题；
3. **构建统一的批流数据平面**：既能够支撑日终批处理和历史重算，又能够通过 CDC 等方式支持实时 / 准实时写入，让风控、运营和报表在逻辑上依赖同一套指标定义与表结构。

在具体形态上，典型的湖仓一体架构可以用下面这幅简化示意图来概括（教学示例）：

```text
# 银行湖仓一体端到端链路示意（简化版）
核心交易数据库  -->  Flink CDC  -->  Iceberg/Hudi 表（交易明细）
                                   |
                                  / \
                     Spark 批处理 /   \ Trino/Presto 即席查询
                                 \   /
                           风控 / 运营 / 报表系统
```

其中，Flink CDC 负责从核心交易数据库捕获变更并实时写入 Lakehouse 表；Spark 等批处理引擎负责在较大的时间窗口内进行复杂汇总和离线分析；Trino / Presto 等交互式查询引擎则为风控、运营、报表等应用提供低延迟查询能力。这三类计算模式共享同一套 Iceberg / Hudi 表，使得“线上近实时视图”和“离线历史视图”在逻辑和口径上保持一致。

#### 1.3.2 湖仓表设计示例：跨行转账对账表

为了更直观地理解 Lakehouse 在银行对账场景中的落地方式，可以以基于 Iceberg 的对账结果表为例，展示其在“表定义层面”与传统 Hive 表的差异（教学示例）：

```sql
-- 提示：基于 Iceberg 的跨行转账对账结果明细表示例
CREATE TABLE bank_reconciliation_iceberg (
    batch_date       DATE,             -- 对账批次日期
    channel          STRING,           -- 渠道类型：MOBILE / WEB / ATM 等
    trans_seq_no     STRING,           -- 交易流水号
    internal_amount  DECIMAL(18,2),    -- 内部交易金额
    external_amount  DECIMAL(18,2),    -- 外部对账金额
    recon_result     STRING,           -- 对账结果：MATCH / DIFF / MISSING
    update_time      TIMESTAMP         -- 最近一次写入时间
)
USING iceberg
PARTITIONED BY (days(batch_date))
TBLPROPERTIES (
    'format-version' = '2',
    'write.format.default' = 'parquet'
);
```

在此基础上，银行可以通过 Flink CDC 或 Spark Streaming 持续将对账结果写入该表，实现实时 / 准实时的对账状态更新；与此同时，借助 Iceberg 的 Snapshot 与 Time Travel 能力，可以方便地完成以下工作：

- 在合规或稽核需要时，回溯某一时刻的对账状态，用于问题调查和证据保全；
- 在调整对账逻辑或口径后，通过新旧快照的对比进行灰度验证或快速回滚；
- 在出现问题时，将上游变更与下游报表之间的关系串联起来，为合规审计与问题追踪提供技术支撑。

#### 1.3.3 与前两阶段的对比小结

综合前文分析，可以将同一银行在三个阶段的核心差异概括为：

- **数据仓库阶段**：以 T+1 监管报表和历史分析为主，强调统一口径和高数据质量，但对实时性支持有限；
- **数据湖阶段**：数据类型与规模大幅扩展，“能存能看”的能力显著提升，但由于缺乏系统性治理，目录和元数据容易失控，整体质量与一致性难以保障；
- **湖仓一体阶段**：在数据湖之上重建表级事务和治理能力，同时支撑批处理与流式更新，逐步演化为承载报表、风控、运营和数据科学的统一平台基座。

#### 1.3.4 三阶段性能与成本对比（银行案例小结）

下表总结了同一银行在三种架构下对“跨行转账对账”场景的一组关键指标差异（教学示例），用于对前文三个阶段的性能与成本特征做集中回顾：

| **维度**             | **数据仓库阶段**                     | **数据湖阶段**                                | **湖仓一体阶段**                                         |
| :------------------- | :----------------------------------- | :-------------------------------------------- | :------------------------------------------------------- |
| **对账口径一致性**   | 高，依赖严格数仓建模与批处理         | 中，部分分析直接读 Raw/Clean 层，口径容易分裂 | 高，统一在 Lakehouse 表上建模，批流共享同一指标定义      |
| **数据更新时效**     | T+1，日终批处理                      | 近实时写入可行，但下游读取易出现不一致        | 分钟级甚至秒级，支持 CDC 流式写入与快照级读写隔离        |
| **报表与分析性能**   | 稳定，主要依赖 MPP / Hive 分布式查询 | 取决于文件数量与目录管理状况，易受小文件影响  | 依托表级元数据与 Data Skipping，复杂查询也能保持稳定性能 |
| **存储成本**         | 中等及以上，部分历史数据难以及时下沉 | 低，用对象存储长期保留原始与历史数据          | 低，在湖上实现数仓能力，避免重复存储与多套体系维护       |
| **数据治理与合规**   | 有一套，但侧重结构化监管报表         | 弱，历史版本与删除管理困难                    | 强，基于 ACID 与 Time Travel 做到精细追溯与敏感数据擦除  |
| **建设与运维复杂度** | 高，建模与调度体系复杂               | 初期较低，后期沼泽化后治理成本陡增            | 中等，通过 Table Format 规范化后，长期运维成本相对可控   |

从该对比表可以看出，数据仓库阶段在对账口径一致性和监管报表支撑方面具有明显优势，数据湖阶段在数据类型与存储成本上更具弹性但治理难度显著提升，而湖仓一体阶段通过在数据湖之上引入表级事务与治理能力，在一定程度上兼顾了实时性、正确性和可追溯性。结合前文的银行案例，可以从“业务指标是否可解释”“治理成本是否可控”“性能是否随时间推移而退化”三个角度理解各阶段架构选择的适用边界与演进方向。

后续章节将基于这一案例，总结出数据架构演进的一般规律，并深入分析 Lakehouse 相关的核心技术。

## 第 2 章 数据架构的代际演变

大数据技术的发展并非一蹴而就，而是随着业务需求（从 T+1 到实时）、数据类型（从结构化到非结构化）和成本考量而不断演进的。本章通过典型应用场景和架构拆解，梳理这一演变过程。在第 1 章中，我们以某商业银行的跨行转账对账业务为主线，观察了同一业务在“数据仓库—数据湖—湖仓一体”三个阶段中的演进；本章则从更普遍的行业实践出发，对这三代数据架构的典型形态和共性特征进行抽象与对比。

### 2.1 第一代：数据仓库（Data Warehouse）的回顾与局限

在企业信息化建设的早期，大型银行、电信、零售等行业普遍采用 Teradata、Oracle Exadata、Greenplum 等传统 MPP 数据仓库，用专用存储与计算集群承载结构化分析负载。进入大数据时代之后，基于 HDFS 的 Hive 数仓在整体设计思路上延续了这些传统数仓的理念，只是在实现上从专有一体机转向了通用服务器和开源软件。在前面的学习中，我们已经学习了 Hive 和数仓建模。本节将传统 MPP 数仓和 Hive 数仓统称为“第一代数据仓库架构”，重点回顾这一代架构的典型应用场景、主要特征以及在成本、数据类型和时效性方面的局限。

#### 2.1.1 典型应用场景：电商离线数仓

以大型电商平台为例，每天会产生大量订单、支付、退款、流量等数据，以及由此衍生的优惠券、会员积分、广告投放等业务事件。早期在**传统 MPP 数仓**和后来的 **Hive 数仓**体系下，典型的做法可以概括为**三步**：

- 将业务库（MySQL / PostgreSQL 等）中的交易、用户、商品等核心表，通过 **ETL 工具**按天抽取到数据仓库的 **ODS 层**或 Hadoop 集群上的 **HDFS** 上，完成基础清洗与脱敏；
- 在数仓内部按照主题构建 **ODS / DWD / DWS / ADS** 等分层，将订单事实、用户维度、商品维度、时间维度等组织成符合**星型 / 雪花模型**的结构，为后续统计分析与报表查询提供统一的数据视图；
- 基于这些事实表和维度表，每晚**离线跑批**生成**运营报表、经营分析、AB 实验结果、渠道转化分析**等，供运营、产品和管理层在第二天使用。

在这一代架构中，“**按主题建模 + 星型模型**”是最典型的数仓建模方式。星型模型的基本形态可以示意如下：

```text
# 电商离线数仓的典型星型模型示意（教学示例）
   dim_user        dim_product        dim_date
      |                |                |
      +----------------+----------------+
                       |
                  fact_order
```

在这种架构中，无论底层实现是**传统 MPP 数仓**还是基于 HDFS 的 **Hive 数仓**，数仓系统都承担了“围绕主题**统一数据口径**、**沉淀历史数据**并支持**多维分析**”的核心职责。

> 从建模形态来看，**星型模型**通常指“一张中心的事实表连接多张维度表”，强调查询时的简洁性与直观性；**雪花模型**则在此基础上对部分维度进一步拆分和规范化，以减少维度冗余、提升结构灵活性，两者共同构成了传统数仓时代最具代表性的建模方式。

#### 2.1.2 架构特征与优势

从整体架构上看，第一代数据仓库通常采用类似“**在线业务库 → ETL → 数仓集群 → 报表 / BI / 分析**”的形态：前端有承载订单、支付等在线交易的 OLTP 数据库，中间通过专门的 ETL 工具在日终窗口抽取、清洗并装载数据，后端则是由传统 MPP 数仓或 Hive 数仓组成的分析型集群，以及接入其上的报表系统和 BI 工具。

在这样的典型架构下，可以从组件构成、数据模式和处理时效三个方面概括其特征：

- **核心组件**：在商业实现中通常以 Teradata、Oracle Exadata、Greenplum 等 **MPP 数仓**为代表，在开源 / 大数据实现中则以 **Hive + HDFS + MapReduce / Tez / Spark** 为主，共同承担数据存储、计算调度和元数据管理等职责；
- **数据模式**：典型采用 **Schema-on-Write（写时模式）**，数据在写入前必须经过清洗、标准化和维度建模，只有满足预定义 Schema 的记录才能进入数仓，从而保证后续报表和分析的口径稳定；
- **处理时效**：以 **T+1 日终批处理** 为主，绝大多数统计、报表和对账任务都会被集中安排在凌晨批量执行，次日白天主要以查询和分析为主。

得益于这样的设计，第一代数据仓库在两个方面表现出特别突出的优势：一是通过统一的维度和指标体系，实现了跨系统、跨部门的**统一数据口径**，极大降低了对账和沟通成本；二是依托类似 SQL 的查询语言（商业 MPP SQL / **Hive SQL**），显著**降低了数据分析的使用门槛**，使 BI、数据分析师和部分业务人员可以直接基于数仓开展各类报表与探索性分析工作。

从相关术语来看，可以把承载在线交易、保证事务一致性的业务数据库称为 **OLTP（Online Transaction Processing）系统**，对应“订单落单、支付扣款”这类高并发、小事务操作；而以批量统计、多维分析为主的数仓与 BI 查询则属于 **OLAP（Online Analytical Processing）工作负载**，更关注聚合、钻取和历史对比。在企业实践中，经常会在企业级数据仓库之上，为某个部门或业务线构建较小范围的 **数据集市（Data Mart）**，本质上是围绕特定主题或团队的子数仓，复用上游统一口径，但在模型粒度和指标选择上更加贴近本部门的分析需求。

#### 2.1.3 面临的挑战

随着业务规模扩大、在线化程度提高以及实时性诉求不断增强，第一代数据仓库架构的局限性也日益突出，主要体现在以下几个方面：

1. **成本与扩展性瓶颈**  
   虽然 Hadoop 在一定程度上缓解了存储成本问题，但无论是传统 MPP 数仓，还是早期“Hive + HDFS” 集群，计算与存储资源往往仍然**强耦合**：一旦需要提升算力，常常被迫同时扩容存储；集群规模增大后，Hive Metastore 中需要维护海量分区与文件元数据，运维复杂度和成本显著上升。

2. **数据类型支持有限**  
   第一代数据仓库在处理结构化表格数据（事实表 + 维度表）方面具有明显优势，但对半结构化数据（例如 JSON / XML 嵌套结构）以及非结构化数据（图片、音视频、日志文本等）的支持能力较弱。现实项目中，接入一类新数据类型往往意味着**额外建设一套采集管道和表结构**，增加了整体系统的碎片化程度。

3. **缺乏灵活的 ACID 事务能力**  
   传统 MPP 数仓通常具备较强的事务能力，但成本高昂且扩展弹性有限；Hive 虽然在后期版本中引入了 ACID 支持，但依赖特定的存储布局，并伴随较高的合并开销，在大规模并发更新与删除场景下表现并不理想。这使得第一代架构难以支撑诸如用户画像实时修正、风控规则高频更新等高变更场景。

4. **时效性不足与实时架构割裂**  
   以 **T+1 批处理** 为主的运行模式天然难以支持分钟级监控和实时运营需求。面对实时推荐、实时风控、实时风格化运营等新兴场景，企业往往不得不在第一代数仓之外**额外搭建一套实时链路**（如专门的流处理和 KV 存储系统），离线数仓与实时系统各自为政，架构割裂、口径难以统一。

### 2.2 第二代：数据湖（Data Lake）的兴起与“沼泽化”

在第一代数据仓库架构中，结构化表格数据得到了良好的建模和分析支持，但在**数据类型多样化**和**长期存储成本控制**方面的能力十分有限。随着日志、埋点、画像特征、模型训练样本等新型数据源的迅速涌现，业界开始尝试构建一种以低成本存储为核心、可以“先存后用”的统一数据承载层，这便是**数据湖（Data Lake）**。

#### 2.2.1 数据湖的目标与典型形态

从宏观目标上看，数据湖希望在不替代现有数仓的前提下，补足两类能力：一是以**较低成本承载更多类型、生命周期更长的原始数据**；二是为后续的数仓建模、特征工程和数据产品提供一个**统一的数据底座**。

围绕这一目标，可以用三条“核心理念”来概括典型数据湖的设计思路：

- 一切数据都可以先“倒”进来，做到“数据不丢”，即使暂时没有明确的使用场景，也先以原始形态保留下来；
- 存储尽可能使用 **HDFS / S3 / OSS / Azure Blob Storage** 等低成本对象存储或分布式文件系统，把存储与计算解耦，降低长期留存成本；
- 在读取阶段再决定如何解析数据，也就是采用 **Schema-on-Read（读时模式）**，让不同的计算引擎可以按需、以各自的方式解释同一批底层文件。

在具体落地时，很多企业会采用类似下述的目录结构，将原始数据、清洗结果、特征数据和“建在湖上的数仓层”分层管理（教学示例）：

```text
# 某企业数据湖 HDFS / 对象存储目录示意（简化版）
/data_lake
  /raw                 # 原始层，直接落盘的日志 / 业务快照
    /nginx_logs
    /app_events
    /db_snapshot
  /clean               # 清洗层，完成基础质量校验与轻度转换
    /nginx_logs_parquet
    /app_events_parquet
  /feature             # 特征层，供推荐 / 风控等下游模型使用
  /warehouse           # 在数据湖之上的数仓层（Hive / Lakehouse）
```

这种做法极大降低了“把数据存下来”的门槛，让企业可以在同一套低成本存储之上同时承载实时日志、离线快照、特征数据和衍生数仓表，也为日后构建数仓、特征库和各类数据产品打下了基础。

#### 2.2.2 “数据沼泽”（Data Swamp）问题

然而，单靠“把数据先放进湖里”并不能自动带来良好的数据资产。随着数据量和数据源数量的快速增长，如果缺乏相应的治理能力，数据湖很容易从“统一数据池”演变为难以维护的“数据沼泽（Data Swamp）”，典型问题包括：

1. **脏数据泛滥与语义模糊**  
   在缺乏强 Schema 约束和统一规范的前提下，写入失败可能留下半截文件或不完整分区；不同团队各自定义目录结构和命名规则，文档不完善甚至缺失，导致很难弄清楚某个目录下的数据究竟代表什么含义、来源于哪个系统、是否仍然在被使用。

2. **读写冲突与一致性问题**  
   对象存储通常只提供**最终一致性**语义，而非数据库级强一致性。当一个任务正在向某个目录写入 Parquet 文件时，另一个查询任务可能会在中间过程读到未写完的数据；在缺乏事务边界的情况下，很难保证“要么读到旧版本，要么读到新版本”，对依赖精确结果的任务构成潜在风险。

3. **数据不可变带来的治理困难**  
   在 HDFS / S3 这类存储系统上，修改数据往往意味着“重写整批文件”，对于需要删除或更正部分记录的场景（例如用户行使 **GDPR** 等隐私合规权利）而言，成本高昂且操作复杂。缺乏行级删除和版本管理能力，也使得精确回溯某一历史时刻的湖中数据状态变得困难。

4. **性能陷阱：小文件与元数据风暴**  
   为了提高更新频率，越来越多任务采用流式写入或高频小批量写入方式，久而久之在某些目录下积累了海量小文件。NameNode 或对象存储的元数据服务因此承受巨大压力，任何全表扫描或分区扫描都需要列举并打开大量文件，查询延迟和资源消耗变得难以控制。

这些问题从根本上反映出：**数据湖在“低成本地存数据”方面非常成功，但在“系统性地管数据、用数据”方面仍然缺乏配套机制**。在这一阶段，业界逐渐意识到，仅有对象存储和文件格式还不够，还需要在数据湖之上重建类似数据库的表级管理能力，这也为后续 Lakehouse 形态的出现埋下了伏笔。

### 2.3 第三代：湖仓一体（Lakehouse）

在第一代数据仓库与第二代数据湖并存的阶段，企业一方面依赖数仓提供稳定可靠的监管报表和历史分析能力，另一方面又希望利用数据湖承载更多类型的数据并降低存储成本。然而，前文已经看到，数据湖虽然解决了“能存、能放”的问题，却在事务、一致性、版本管理和治理方面存在明显短板。为在不放弃数据湖优势的前提下补齐这些能力，业界逐步形成了第三代数据架构形态——**湖仓一体（Lakehouse）**。

#### 2.3.1 定义与设计目标

从概念上看，Lakehouse 可以被理解为“**建在数据湖之上的数仓级表管理层**”：它以 Parquet 等开放文件格式和对象存储 / HDFS 为基础存储，将传统数仓才具备的 ACID 事务、Schema 管控和高性能查询能力下沉到数据湖之上，并通过标准化的表格式（Table Format）对外提供统一的表视图。

围绕这一思路，典型 Lakehouse 系统通常有三大设计目标：

1. 在底层继续利用对象存储 / HDFS 的**低成本与高扩展性**，继承数据湖“能放得下、放得久”的优势；
2. 在表级引入类似 MPP 数仓的**数据管理能力与查询性能**，包括 ACID 事务、快照隔离、数据跳过（Data Skipping）等，使复杂分析在湖上也能稳定运行；
3. 尽量保持对计算引擎的**中立性**，让 Spark、Flink、Trino、Presto、StarRocks 等多种引擎可以通过统一的表格式和 Catalog 访问同一套 Lakehouse 表，避免被单一引擎锁定。

#### 2.3.2 Data Warehouse / Data Lake / Lakehouse 对比

为了把 Lakehouse 放在完整的演进路径中理解，可以从存储介质、数据模型、模式时机、事务能力、时效性和引擎绑定程度等维度，对三代架构进行对比（教学示例）：

| 维度             | Data Warehouse                             | Data Lake                      | Lakehouse                                                    |
| :--------------- | :----------------------------------------- | :----------------------------- | :----------------------------------------------------------- |
| 存储介质         | 专有存储 / MPP 节点本地盘                  | HDFS / 对象存储                | HDFS / 对象存储                                              |
| 数据模型         | 强 Schema，结构化为主                      | 弱 Schema，支持任意格式        | 在湖上施加 Schema 与约束                                     |
| 模式时机         | Schema-on-Write                            | Schema-on-Read                 | 读写结合：写入时校验，读取时可演进                           |
| 事务能力         | 强 ACID                                    | 无事务或弱事务                 | 基于 Table Format 提供 ACID / MVCC                           |
| 时效性           | T+1 批处理为主                             | 可以近实时写，但一致性问题突出 | 既可支撑批处理，又可支撑流式 / 近实时写入                    |
| 计算引擎绑定程度 | 与内部引擎强绑定                           | 弱绑定，主要依赖文件格式       | 尽量引擎中立，通过开放规范与 Catalog 对接                    |
| 典型技术代表     | Teradata / Greenplum / Snowflake（云数仓） | HDFS + Hive / S3 + EMR         | Iceberg / Hudi / Delta Lake + Spark / Flink / Trino / Presto |

从表格可以看出，Lakehouse 并不是“再造一个数仓”，也不是简单的“给数据湖套一层外壳”，而是在数据湖之上构建了一层标准化的表管理能力：既保留湖的低成本和开放性，又通过 Table Format 为上层计算引擎屏蔽底层存储的复杂性，并在事务、一致性和时效性之间寻求更好的平衡。

## 第 3 章 核心技术基石：Table Formats（表格式）

Lakehouse 之所以能成立，核心在于引入了 **Table Format（表格式）** 这一中间层。它不是一个具体的计算引擎，而是一套“如何在文件之上管理表”的协议与实现。在第 2 章中，我们从架构视角分析了三代数据架构以及 Lakehouse 的整体形态，本章将聚焦于支撑 Lakehouse 的核心技术机制——`Table Format`。

通过本章的学习，读者应当能够回答两个问题：

1. 为什么单靠 Hive Metastore + 目录结构无法满足现代数据湖的需求？
2. Table Format 具体多做了哪些事情，使得在对象存储上也可以拥有接近数据库的体验？

### 3.1 什么是 Table Format？

在传统 Hadoop 体系中，我们只有 **File Format**（文件格式，如 Parquet、ORC、Avro）和 **Table**（Hive Metastore 中的表定义）。从第 2 章的角度来看，File Format 主要对应“如何把数据高效地存到湖里”，而 Table Format 则对应“如何在这些文件之上构建稳定可管的表”。

- **File Format**：解决了“如何高效存储数据”的问题（列式压缩、编码、向量化读取）。
- **Table Format**：解决了“哪些文件属于这张表，以及如何在多版本之间切换”的问题。

在 Hive 中，“属于这张表的文件”由**目录（Directory）**隐式定义（例如 `hdfs:///warehouse/db/table/dt=20231213/`）。这一方案存在明显缺陷：

> 缺陷：Listing 一个包含数万个文件的目录非常慢（在 S3 上尤为明显），且无法原子性地变更目录下的文件列表。一旦中间出现失败，目录内容可能处于“半更新”状态。

**现代 Table Format**（如 Apache Iceberg）通过**显式元数据文件（Metadata Files）**来精确追踪每一个数据文件，避免了对目录 Listing 的依赖。

### 3.2 业界主流“三剑客”对比

围绕上述目标，业界在实践中逐步形成了三种主流 Table Format 实现，它们在起源和侧重点上有所不同：

目前业界主要有三大 Table Format：**Apache Iceberg**、**Apache Hudi**、**Delta Lake**。

| 特性维度     | **Apache Iceberg**                                            | **Apache Hudi**                                                | **Delta Lake**                           |
| :----------- | :------------------------------------------------------------ | :------------------------------------------------------------- | :--------------------------------------- |
| **起源**     | Netflix                                                       | Uber                                                           | Databricks                               |
| **设计初衷** | 解决 S3 上大规模数据目录 Listing 慢的问题，提供严格的快照隔离 | 解决流式数据的快速 Upsert / Delete（流式入湖）                 | 深度优化 Spark 性能，提供数仓级体验      |
| **核心亮点** | Hidden Partitioning（隐藏分区）、设计简洁、引擎中立           | Copy-On-Write (COW) / Merge-On-Read (MOR) 双模式、索引能力丰富 | Z-Order 排序优化、Data Skipping 性能极强 |
| **适用场景** | 通用离线 / 近实时数仓，元数据管理要求高                       | 高频 CDC、实时更新 / 删除场景                                  | Spark 生态为主，追求高性能交互式查询     |

在本课程中，我们主要以 **Iceberg** 为代表进行原理讲解，读者在理解其核心思想后，可以类比理解 Hudi 与 Delta Lake。

### 3.3 Table Format 解决的关键问题

综合第 1 章的银行案例和第 2 章的三代架构对比，可以看到，要想在数据湖之上实现 Lakehouse 所承诺的事务能力、一致性保证和统一批流视图，仅仅依靠对象存储和目录结构远远不够。Table Format 正是为了解决以下几类共性问题而设计的：

1. **元数据可扩展性**  
   在传统“目录即元数据”的方案中，目录 Listing 成为性能瓶颈，目录层级和文件数量一旦增大，管理和查询成本都会急剧上升。Table Format 通过使用多层次元数据文件（例如 Manifest / Snapshot / Metadata）替代目录 Listing，可以在数十亿级别的数据文件规模下仍然保持可接受的管理与查询性能，对应解决了第 2 章中“数据湖目录和元数据易失控”的痛点。

2. **多版本并发控制（MVCC）**  
   数据湖阶段缺乏明确的事务边界和版本管理，容易出现“半写入目录被误读”“难以回溯某一历史状态”等问题。Table Format 通过 Snapshot 机制实现读写隔离，新写入不会影响正在进行的查询，并支持“快照回滚”“时间旅行”等高级能力，从而在湖上实现类似数据库的 MVCC 语义，呼应了第 2 章中对事务性和可回溯性的需求。

3. **Schema 演进与数据演进解耦**  
   在实际生产中，字段新增、类型调整、字段重命名是常态，如果仅依赖目录和文件名管理 Schema，往往会导致历史数据不可读或多版本兼容困难。现代 Table Format 支持字段新增、类型调整、重命名等操作，并通过字段 ID 而非字段名进行绑定，避免简单重命名导致的兼容性问题，从而在不重写全部历史数据的前提下支撑 Schema 演进。

4. **统一批流写入模型**  
   第一代架构中，离线数仓与实时链路往往割裂；在数据湖阶段，流式写入又带来了小文件和一致性问题。Table Format 在设计上同时支持批任务一次性生成大量文件，以及流任务以小批量 / 高频方式持续写入，再结合 Compaction 机制对小文件进行合并，从而在同一套 Lakehouse 表中实现统一的批流写入模型，为第 1 章和第 2 章中提到的“批流一体”提供了落地基础。

## 第 4 章 核心机制剖析

本章聚焦 Lakehouse 在工程实现层面的“关键内功”，围绕 Iceberg 表格式的内部机制进行拆解。与第 1 章的银行案例和第 2 章的三代架构抽象相呼应，本章将依次回答三个问题：第一，Iceberg 如何通过多层元数据结构在对象存储之上重建表级视图与版本管理；第二，它是如何在不可变文件系统上实现 Copy-On-Write 写入、快照隔离与时间旅行，从而提供接近数据库的 ACID 语义；第三，它又如何通过隐藏分区、Data Skipping、快照保留与垃圾回收等机制，在保证实时性与一致性的同时控制查询开销与存储成本。

### 4.1 元数据层（Metadata Layer）设计

Iceberg 的元数据管理是其核心。它将元数据分为多层，实现了自底向上的管理与优化。相较于“目录即元数据”的传统方案，Iceberg 将“哪些文件属于这张表、历史上出现过哪些版本、当前版本由哪些文件组成”等信息显式写入元数据文件中，从而在规模扩大时仍然保持可管理性与可观测性。

```text
# 例子：bank_reconciliation_iceberg（跨行对账结果表）的元数据层级关系

   +---------------------+
   |   Catalog           |
   | (指向当前 Metadata) |
   +----------+----------+
              |
              v
   +---------------------+
   |   Metadata File     |
   | (表定义 + Snapshot) |
   +----------+----------+
              |
              v
   +---------------------+
   |    Manifest List    |
   | (一个快照的清单表)  |
   +----------+----------+
              |
              v
   +---------------------+
   |    Manifest File    |
   | (一批 Data File 信息)|
   +----------+----------+
              |
              v
   +---------------------+
   |      Data File      |
   | (对账结果 Parquet / |
   |  ORC 数据文件等)    |
   +---------------------+
```

1. **Data Files**：底层的 Parquet / ORC 数据文件，存放真实业务数据。
2. **Manifest Files（清单文件）**：记录一批 Data File 的路径、分区信息、文件级统计信息（行数、列 Min / Max 值等）。
3. **Manifest List**：一个快照（Snapshot）对应一个 Manifest List，它记录了构建当前表状态所需的所有 Manifest Files。
4. **Metadata File**：定义表的 Schema、分区策略以及当前最新的 Snapshot ID，同时维护 Snapshots 列表。
5. **Catalog Reference**：存放对“当前 Metadata File” 的指针，通常托管在 Hive Metastore、RDBMS 或专用 Catalog 服务中。

在这张图中，最底层的 Data File 使用的是 Parquet / ORC 等 **File Format（文件格式）**，主要解决的是“单个文件内部如何高效存储与压缩数据”的问题；Iceberg 则是一个 **Table Format（表格式）**，站在这些文件之上，负责“这一整张表由哪些文件组成、有哪些历史版本、当前快照包含哪些文件、如何提供 ACID 语义与时间旅行”等表级管理能力。二者不是互相替代的关系，而是分层配合：工程实践中常见的组合就是“**Iceberg 表 + 底层 Parquet 文件**”。

示例（高度简化后的 Iceberg Metadata JSON 片段）：

```json
// 提示：简化后的 Iceberg Metadata File 结构示例
{
  "format-version": 2,
  "table-uuid": "1234-5678-90ab-cdef",
  "location": "hdfs://namenode:8020/warehouse/db/table",
  "last-updated-ms": 1700000000000,
  "current-snapshot-id": 101,
  "snapshots": [
    {
      "snapshot-id": 101,
      "timestamp-ms": 1700000000000,
      "manifest-list": "s3://bucket/db/table/metadata/snap-101.avro"
    }
  ]
}
```

这个 JSON 文件本质上是“表的总目录”，而目录下的快照与 Manifest 则进一步指向真正的数据文件。结合第 1 章的银行案例，可以理解为：同一张跨行对账表在不同时刻的“对账结果快照”都被记录在 Metadata File 中，而 Catalog 只需要指向“当前使用哪一个快照”即可。

### 4.2 读写操作原理：Copy-On-Write

如果说 4.1 小节回答的是“元数据长什么样、在哪里”，那么本小节要回答的是“在这些元数据之上，**一次写入和一次读取到底发生了什么**”。我们将从写入路径、读取路径和并发控制三个角度拆解 Iceberg 的 Copy-On-Write 机制，说明它如何在不可变文件系统上实现接近数据库的 ACID 语义，并支撑第 1 章中银行跨行对账场景中的 CDC 实时入湖与历史更正需求。

#### 4.2.1 写入路径与 ACID 语义

在不可变文件系统上实现 `UPDATE` 或 `DELETE`，核心思想是使用 **Copy-On-Write**：不直接修改旧文件，而是写出新文件，再通过快照切换暴露新版本。一次“写入并提交”的过程既是对数据文件的更新，也是对“当前快照指针”的原子性更新。

**写入流程（写新快照）**：

1. 从 Catalog 读取当前 Metadata File（例如 v1.json），得到 current snapshot = 100；
2. 基于 current snapshot 读取需要更新的数据（例如某个分区）；
3. 计算引擎（Spark / Flink）生成新的 Parquet 文件集合；
4. 写入新的 Manifest File（记录新文件及其统计信息）；
5. 写入新的 Manifest List（描述本次快照使用了哪些 Manifest Files）；
6. 生成新的 Metadata File（v2.json），将 current snapshot 指向新快照 ID = 101；
7. 尝试向 Catalog 提交 v2.json 的引用（原子更新），提交成功后，对外可见的新版本即为 101；
8. 老的快照（100）处于“可回滚 / 可查询”的历史状态。

从 ACID 角度解读上述流程：

- **原子性（Atomicity）**：要么 Catalog 成功切换到新 Metadata File，要么保持指向旧版本，不会出现“部分文件可见、部分不可见”的中间状态；
- **一致性（Consistency）**：只有通过完整快照提交流程生成的新版本才会对外可见，所有读者看到的都是“某个快照下的一致视图”；
- **隔离性（Isolation）**：正在进行的查询会一直基于其启动时绑定的快照读取数据，即使有新的快照提交也不会干扰当前查询；
- **持久性（Durability）**：一旦快照提交成功并持久化到 Metadata / Manifest / Data Files，对外暴露的版本在存储层不会“悄然消失”，除非显式执行快照过期与垃圾回收。

#### 4.2.2 读取流程与快照隔离

**读取流程（读取最新快照）**：

1. 从 Catalog 获取当前 Metadata File 的位置；
2. 解析 Metadata File，得到当前 Snapshot ID；
3. 加载对应的 Manifest List，进而加载若干 Manifest Files；
4. 根据查询条件（过滤字段、分区字段等）在 Manifest 中进行**文件级裁剪（Data Skipping）**；
5. 对剩余文件执行向量化扫描，返回查询结果。

在这个过程中，“读取哪一个快照”是由读取侧显式或隐式决定的：

- 如果不指定时间或快照 ID，则读取 Catalog 指向的**最新快照**；
- 如果通过 Time Travel 语法指定时间或快照 ID，则读取对应的**历史快照**；
- 读取过程中不会看到写入尚未提交的新文件，从而实现了“读写分离”和快照级隔离。

#### 4.2.3 并发控制与 CDC Upsert / Delete

在实际生产中，不同作业可能同时向同一张 Iceberg 表写入数据（例如多个 Flink CDC 任务或批处理任务并行运行）。Iceberg 采用**乐观并发控制（Optimistic Concurrency Control）**来处理这种场景：

1. 每个写入任务在开始时都读取当前 Metadata File 及其快照 ID，基于该快照生成新的数据文件和 Manifest；
2. 在提交时，任务会检查当前 Catalog 中记录的最新快照 ID 是否仍然是自己开始时看到的那个；
3. 如果一致，则可以安全提交；如果已经被其他任务更新，则当前任务需要重新基于新的快照重放写入或合并变更。

在 CDC 和行级变更场景中，Iceberg 通过两类 Delete File 来支持 Upsert / Delete 语义：

- **Equality Delete**：记录“满足某些键值条件的行应被视为删除”，适用于按主键删除或更新；
- **Position Delete**：记录“某个数据文件中某些具体行的位置应被视为删除”，适用于更细粒度的修正。

结合第 1 章的银行案例，可以这样理解：

- Flink CDC 作业将跨行对账的增量变更不断写入 Iceberg 表，通过 Upsert 保持对账结果表的**近实时最新状态**；
- 当需要更正历史对账结果或执行合规删除时，可以通过 Delete + 重新提交快照的方式实现**精确的数据修正与擦除**，而不会破坏其他查询正在使用的快照视图。

### 4.3 时间旅行（Time Travel）

在了解了“写入如何生成新快照、读取如何选择快照”之后，本小节进一步回答：**如何在同一张表上回看任意历史时刻的状态**。Time Travel 机制允许我们在不复制整张表的前提下，基于历史快照进行查询，这既是湖仓一体实现合规追溯与问题排查的基础，也是机器学习场景中重放历史特征的关键能力。

由于每次提交都会生成一个新的 Snapshot，且旧的 Snapshot 和数据文件不会立即删除，我们可以轻松查询历史时刻的数据状态。

不同引擎在 SQL 语法上的具体写法略有差异，下面的示例可以理解为一段“伪代码风格”的教学用示意，用来说明“按时间点 / 按版本号查询”的基本思想：

```sql
-- 示例：按时间点查询某一历史状态（伪代码示意）
SELECT * FROM my_table TIMESTAMP AS OF '2023-12-12 10:00:00';

-- 示例：按快照 ID 查询对应版本（伪代码示意）
SELECT * FROM my_table VERSION AS OF 123456789;
```

典型应用包括：

- 追溯某个线上报表在某天的计算口径与原始数据；
- 回放历史数据，重训机器学习模型；
- 在更新出现问题时，快速回滚到上一个稳定快照。

### 4.4 隐藏分区（Hidden Partitioning）

有了快照与事务之后，还需要回答“**如何在不增加建模负担的前提下，让查询只扫该扫的数据**”。本小节从分区与数据剪枝的角度出发，介绍 Iceberg 的隐藏分区与 Data Skipping 机制，解释它如何在保持对业务字段友好的同时，自动完成分区映射与文件级裁剪，从而在银行对账等场景中兼顾易用性与查询性能。

在 Hive 中，如果按天分区，我们需要显式增加一个 `dt` 字段（如 `dt = '2023-12-13'`），并在查询时写 `WHERE dt = '2023-12-13'` 才能利用分区剪枝。

Iceberg 支持 **隐藏分区（Hidden Partitioning）**：

- 在建表时定义分区策略为 `days(ts)`，其中 `ts` 是事件时间列；
- 写入时，Iceberg 自动将时间戳映射到日期分区，无需显式的 `dt` 列；
- 查询时，用户只需写：

```sql
-- 提示：Iceberg 隐藏分区下的查询示例
SELECT *
FROM user_events
WHERE event_time >= '2023-12-12' AND event_time < '2023-12-13';
```

Iceberg 会自动将时间过滤条件下推到分区层面，实现高效的分区裁剪，而用户无需关心底层分区字段的命名与编码方式。

在隐藏分区之外，Iceberg 还依托 Manifest 中记录的**列级统计信息**实现更细粒度的 **Data Skipping**。每个 Manifest File 中都会保存该批数据文件在某些字段上的最小值 / 最大值、空值数量等统计信息，当查询条件中包含这些字段时，Iceberg 可以在“不真正打开数据文件”的前提下，先基于统计信息过滤掉不可能命中的文件，从而显著降低扫描数据量。对于第 1 章中的银行对账场景，这意味着在只查询某一天、某一渠道的对账结果时，无需扫描所有历史分区和所有渠道的数据文件。

### 4.5 一致性与垃圾回收（Retention & GC）

Time Travel 带来了强大的追溯能力，但如果不加控制，历史快照和老文件会越积越多，最终拖垮存储与查询性能。本小节聚焦于 **Retention 策略与垃圾回收机制**，说明 Lakehouse 如何在保证可追溯性的同时，通过有计划地过期快照和清理孤儿文件，维持系统长期运行的稳定性与成本可控性。

在支持时间旅行的同时，Iceberg 需要处理“历史快照与老文件如何清理”的问题：

- 通过保留策略（例如“保留最近 7 天快照”或“保留最近 N 个快照”）控制历史版本数；
- 定期运行 `expire_snapshots` / `remove_orphan_files` 等维护任务，清理不再被任何快照引用的文件；
- 在企业实践中通常结合调度系统（如 Apache Airflow、DolphinScheduler）进行周期性维护。

通过这些机制，Lakehouse 在保证可追溯性的同时，避免“时间旅行导致存储成本无限膨胀”的问题。

### 4.6 与银行湖仓一体案例的对应关系

结合第 1 章的银行案例，可以将本章介绍的机制与具体业务诉求一一对应起来：

1. **统一对账结果视图与监管口径**：通过 Metadata / Snapshot / Catalog 机制，银行可以在 Iceberg 表之上维护一套统一的对账结果视图，不同系统（风控、运营、监管报表）查询到的都是某个快照下的一致数据；
2. **近实时风控与运营看板**：依托 Copy-On-Write 写入路径与乐观并发控制，Flink CDC 等作业可以稳定地向同一张对账结果表持续写入变更，Spark / Trino 等查询引擎则基于最新快照构建分钟级甚至秒级的风控与运营指标；
3. **历史追溯与合规删除**：通过 Time Travel 与 Delete File 机制，银行既可以回溯任意时刻的对账状态，用于问题排查和审计取证，又可以在合规要求下对特定记录进行删除，并结合 Retention / GC 控制历史版本数量；
4. **性能与成本控制**：依托隐藏分区和 Data Skipping，针对特定日期、渠道或机构的查询无需扫描所有数据文件；结合快照过期策略与小文件合并机制，可以在保证性能的前提下控制存储成本，使湖仓一体平台在长期运行中保持可持续性。

通过这一映射，读者可以将“元数据层级、快照与事务、批流一体写入、分区与 Data Skipping、Retention & GC”等抽象机制，与银行跨行对账这一具体场景建立直接联系，形成从业务诉求到技术实现的完整闭环。

### 5.2 典型应用场景方案

在掌握了各层组件的基本职责之后，本小节通过四个具有代表性的应用场景，展示 Lakehouse 在实际数据平台中的常见用法。每个场景都对应一类典型问题：如何实时同步业务库变更、如何统一离线与实时指标、如何在满足合规要求的前提下修正历史数据，以及如何为机器学习提供统一、可回放的特征底座。

#### 场景一：CDC（Change Data Capture）实时入湖

本场景聚焦“**如何用更低的成本、更短的延迟把业务库变更实时同步到湖仓**”。传统数仓通常每天全量同步 MySQL 表，效率低且延迟高；基于 Lakehouse 的 CDC 方案可以将延迟缩短到分钟级甚至秒级，并在表级层面保留 Upsert / Delete 语义。

在第 1 章的银行跨行对账案例中，可以将“核心交易数据库 + Flink CDC + bank_reconciliation_iceberg 表”视作这一场景的具体化：任何一笔跨行转账状态的变更都会通过 CDC 流实时写入湖仓，对账结果表中的状态也随之更新，从而为后续风控与运营指标提供接近实时的数据基础。

典型链路：

1. **Source**：MySQL Binlog（通过 Debezium / Flink CDC 捕获变更）；
2. **Transport**：Flink 作业消费 Binlog 变更事件流；
3. **Sink**：Flink 将 `INSERT / UPDATE / DELETE` 操作流式写入 **Iceberg / Hudi** 表；
4. **Query**：下游 Trino / Spark / StarRocks 直接查询 Lakehouse 表，获取最新状态。

```sql
-- 提示：Flink SQL 流式写入 Iceberg 的教学示例
CREATE TABLE iceberg_table (
    id BIGINT,
    data STRING,
    PRIMARY KEY (id) NOT ENFORCED
) WITH (
    'connector' = 'iceberg',
    'catalog-name' = 'hadoop_catalog',
    'warehouse' = 'hdfs://namenode:8020/warehouse'
);

INSERT INTO iceberg_table
SELECT *
FROM mysql_cdc_source;
```

通过 Table Format 的 Upsert / Delete 支持，我们可以在对象存储之上构建接近 OLTP 语义的“近实时数仓”。

#### 场景二：流批一体（Streaming & Batch Unification）

本场景关注“**如何避免离线链路和实时链路各自为政、口径不一致**”。Lakehouse 的一个重要优势是**存储统一、逻辑统一**：

- 流任务（Flink）和批任务（Spark / Trino）可以共享同一个 Iceberg / Hudi 表；
- 同一套 SQL 逻辑可以同时用于处理历史批数据与未来流数据；
- 避免了“实时链路一套指标定义、离线链路另一套指标定义”的口径不一致问题。

回到银行跨行对账案例：Flink 流任务负责实时写入最新对账结果，Spark 批任务则在更长时间窗口上进行日终汇总与历史分析，两者共享同一张对账结果表和同一套指标定义，从而既满足了监管报表的稳定性，又兼顾了运营与风控的实时性。

#### 场景三：历史数据修正与合规

本场景聚焦“**如何在不重写整库的前提下，精确修正历史数据并满足合规要求**”。在传统数据湖中，对历史数据进行“纠错”“回灌”往往代价巨大；Lakehouse 中，可以通过：

- 使用 `MERGE INTO` 语句，对历史分区数据进行精准修正；
- 利用 Time Travel 对比修正前后的数据，生成审计报表；
- 对于需要删除的敏感数据（例如用户删除请求），通过 Delete + Expire Snapshots 实现真正的数据擦除。

在银行场景下，这对应于“对某批次对账逻辑进行更正或应监管要求删除部分敏感记录”的需求：借助 MERGE 与 Time Travel，既可以对历史对账结果进行定点修正，又可以在必要时精确擦除某些交易记录，同时保留完整的审计链路。

#### 场景四：特征湖与机器学习

本场景关注“**如何为大规模机器学习提供统一、可回放的特征底座**”。在机器学习场景中，特征工程需要对历史数据反复回放与组合：

- Lakehouse 提供高效的列式存储与 Time Travel 能力，便于回放历史时点特征；
- 特征生产任务（批 / 流）均可以写入统一的特征表，供训练与在线服务共享；
- 结合上层特征服务平台（Feature Store），可以构建完整的特征生命周期管理体系。

如果继续扩展第 1 章的银行案例，可以将实时对账结果表和历史交易明细表视作特征湖中的两类原始特征源：风控团队可以在其之上构建交易频率、对账差异率、渠道异常行为等特征视图，既能利用 Time Travel 回放任意历史时点的特征，又能通过流式任务持续更新在线特征，支撑反洗钱、欺诈检测等模型的训练与在线推断。

## 第 6 章 业界主流解决方案与未来展望

在掌握了现代数据栈的组件分层和典型应用场景之后，本章从“技术形态与发展趋势”的角度，概括业界在 Lakehouse 方向的主要实现路径，并从宏观上回顾三代数据架构的演进规律。与前文的技术细节相比，本章更强调对整体图景的理解，而不是具体产品的选型。

### 6.1 商业化平台与开源生态

本小节以代表性平台和方案为例，介绍当下 Lakehouse 相关系统的大致形态。通过对比可以看到：无论是商业化一体化平台、云厂商集成方案，还是基于开源组件自建的体系，核心思路都是在对象存储之上叠加表格式与计算引擎，以实现类似数仓的管理能力。

1. **Databricks Lakehouse**

   - 提出 Lakehouse 概念的公司，核心开源组件为 Delta Lake；
   - 在其平台上，Spark、Delta、ML、BI 紧密集成，强调“一体化数据智能平台”。

2. **Snowflake**

   - 起步于云原生数仓，通过引入 External Table、Iceberg 表支持等机制向 Lakehouse 靠拢；
   - 强调“数据云”理念，可跨云、跨账号共享数据。

3. **云厂商方案（以阿里云为例）**

   - MaxCompute + Hologres + EMR + Data Lake Formation 等产品协同；
   - 通过内置 Hudi / Iceberg 支持，实现湖仓一体的数据平台能力。

4. **纯开源自建方案**
   - 存储层：HDFS / S3 / OSS / MinIO；
   - 表格式层：Iceberg / Hudi / Delta Lake（开源版本）；
   - 计算层：Spark / Flink / Trino / Presto / StarRocks / Doris；
   - 元数据与编排：Hive Metastore / Glue / Nessie + Airflow / DolphinScheduler。

在开源自建体系中，不同组件往往围绕各自擅长的工作负载形成互补关系：以 Apache Iceberg、Apache Hudi、Delta Lake、Apache Paimon 等为代表的 **表格式 / 流式表存储层**，负责在对象存储或 HDFS 之上提供表级事务、版本管理与批流一体写入；以 StarRocks、Apache Doris 等为代表的 **MPP/HTAP 引擎**，则通常作为面向分析与查询的前端引擎，通过 External Table、Lakehouse Catalog 等方式访问同一套湖上表，从而在同一数据基础之上同时支持复杂分析查询与近实时明细查询。其中，**HTAP（Hybrid Transactional/Analytical Processing）** 通常指“在同一引擎或同一平台内同时承载接近实时写入与分析型查询”的混合负载；许多 MPP/HTAP 系统在实现上采用列式存储与向量化执行等典型 **Columnar OLAP** 技术，以便在 Lakehouse 场景下兼顾高吞吐写入与复杂分析性能。

综合以上几类方案，可以主要从以下两个维度来理解它们之间的差异：

- **“全托管平台”与“基于开源组件自建平台”在人力投入、功能弹性和系统可控性方面的不同特点**：前者通常以更高的产品成熟度与更低的运维门槛为主要优势，由平台厂商负责底层资源管理、故障恢复与版本演进，用户主要通过“声明式配置 + 按量付费”的方式获得能力；后者则需要投入更多架构与运维人力来完成组件选型、集群部署、容量规划与升级迁移，但在成本结构、功能组合和技术路线的可控性与灵活性方面拥有更大空间。
- **国内外典型企业在不同发展阶段的演进路径**：许多企业在早期以传统 MPP 数仓或本地 Hadoop 集群作为核心分析平台，随着数据规模增长与业务形态复杂化，逐步迁移到云原生数仓或“对象存储 + Table Format”的数据湖架构；在此基础上，进一步在监管合规、实时性要求以及多云 / 混合云策略等因素驱动下，引入 Lakehouse 能力与多引擎协同方案，实现从“单一数仓”到“湖仓一体平台”的渐进式演进。

### 6.2 思考与总结

本小节从“成本—效率—质量”三个维度回顾本章和前文出现的三代数据架构形态，总结它们各自的优势与局限，并给出若干思考题，帮助读者从更长的时间尺度理解技术演进的内在逻辑。

从 Data Warehouse 到 Data Lake，再到 Lakehouse，本质上是对 **成本**、**效率** 和 **质量** 的不断平衡与再平衡：

- **Data Warehouse**：高质量、高一致性，但成本高、扩展性相对有限；
- **Data Lake**：低成本、高灵活性，但数据质量与治理难度较大；
- **Lakehouse**：试图在低成本之上，通过 Table Format 等软件抽象，重建高质量的数据管理能力。

可以思考以下几个问题，以 **加深对本章内容的理解**：

1. 试分析一家中型互联网公司在数据平台演进过程中，可能依次会遇到哪些与 **成本**、**效率**、**质量** 相关的主要矛盾？
2. 对比 **托管式 Lakehouse 平台** 与 **基于 Iceberg / Hudi 等组件自建的平台**，它们在 **资源弹性**、**功能灵活性** 和 **系统可控性** 方面分别具有哪些典型特征？
3. 随着 **实时性要求** 的不断提升，Lakehouse 与流式数据平台（如 Kafka / Flink）在架构上可能会出现哪些新的 **融合模式**？

作为大数据工程师，**掌握 Lakehouse 架构及 Table Format 原理**，已成为继 Hadoop、Spark 之后的 **新一代基础能力**。在后续学习与实践中，读者可以结合本课程的 **知识框架**，阅读 **Iceberg / Hudi / Delta Lake 的官方文档与论文**，进一步深入理解其设计取舍与实现细节。
