# Window 机制与 Watermark 协同详解

## 1. 概述

在流式计算（Streaming Computing）中，**窗口（Window）** 定义了无限数据流上的有限切片，而 **水印（Watermark）** 则是衡量时间进度的逻辑时钟。两者的协同工作机制是确保计算结果准确性（Correctness）与及时性（Latency）的核心。

本文档旨在直观阐述 **滚动窗口（Tumbling Window）**、**滑动窗口（Sliding Window）** 与 **会话窗口（Session Window）** 如何在 Watermark 的驱动下进行生命周期流转（创建、触发、合并与清理）。

## 2. 窗口生命周期与 Watermark 驱动

Watermark 是窗口状态流转的“发令枪”。一个标准的窗口生命周期包含以下阶段：

1. **创建（Creation）**：当属于该窗口的第一个事件到达时，系统自动创建窗口状态。
2. **触发（Triggering）**：当 `Watermark ≥ 窗口结束时间` 时，触发计算逻辑（如求和、计数）。
3. **允许延迟（Allowed Lateness）**：在 `窗口结束时间 < Watermark < 窗口结束时间 + AL` 期间，迟到数据可触发修正更新。
4. **清理（Purging）**：当 `Watermark ≥ 窗口结束时间 + AL` 时，彻底销毁窗口状态。

## 3. 滚动窗口（Tumbling Window）与 Watermark

### 3.1 机制说明

滚动窗口将时间划分为固定大小、不重叠的区间（如 `[10:00, 10:05)`, `[10:05, 10:10)`）。

- **事件归属**：每个事件仅属于一个窗口。
- **Watermark 作用**：Watermark 就像一条单向推进的“切割线”，每当越过一个切分点（如 10:05:00），即宣告该区间结束。

### 3.2 直观示例

**设定**：窗口大小 5 分钟，Watermark 延迟 0 分钟（理想情况）。

```text
时间轴: | 10:00 --- 10:01 --- 10:02 --- 10:03 --- 10:04 --- 10:05 --- 10:06 |
        [      Window 1 (10:00-10:05)       ]
                                            ^
                                            |
                                  Watermark 到达 10:05:00
                                  -----------------------
                                  触发 W1 计算并输出
```

**行为推演**：

1. **10:01 Event** 到达 -> W1 创建并更新状态。
2. **10:04 Event** 到达 -> W1 更新状态。
3. **Watermark 推进到 10:04:59** -> W1 保持开启，等待。
4. **Watermark 推进到 10:05:00** -> **触发点**！W1 输出结果。若无 `Allowed Lateness`，立即销毁 W1。

## 4. 滑动窗口（Sliding Window）与 Watermark

### 4.1 机制说明

滑动窗口由 **窗口大小（Size）** 和 **滑动步长（Slide）** 定义（如 Size=10m, Slide=5m）。

- **事件归属**：一个事件可能同时属于多个重叠的窗口（例如，10:03 的事件同时属于 `[09:55, 10:05)` 和 `[10:00, 10:10)`）。
- **Watermark 作用**：Watermark 的一次推进可能连续触发多个窗口的结束。

### 4.2 直观示例

**设定**：窗口大小 10 分钟，滑动步长 5 分钟。

```text
时间轴: | 09:55 --- 10:00 --- 10:05 --- 10:10 |
        [    W1 (09:55-10:05)     ]
                    [    W2 (10:00-10:10)     ]
                          ^
                          |
                Watermark 到达 10:05:00
                -----------------------
                触发 W1 结束
                W2 继续等待
```

**关键点**：

- 当 `Watermark = 10:05:00`：
  - **W1** (`09:55-10:05`) 满足 `Watermark ≥ EndTime` -> **触发输出**。
  - **W2** (`10:00-10:10`) 尚未结束 -> **保持开启**。
- **状态复用**：在底层实现中，系统通常不会存储两份完整数据，而是通过“切片（Pane）”复用或针对每个窗口独立维护聚合结果，这取决于具体引擎优化（如 Flink 的 Bucket 机制）。

## 5. 会话窗口（Session Window）与 Watermark

### 5.1 机制说明

会话窗口没有固定起止时间，而是由 **活跃间隙（Session Gap）** 定义。如果两个事件间隔达到或超过 Gap，则分属不同会话。

- **动态合并**：Session Window 是**动态**的。初始时，每个事件都会创建一个独立的 Session 窗口（`[EventTime, EventTime + Gap)`）。
- **生命周期机制**：
  1. **数据驱动合并**：当新事件到达，若其时间范围与现有窗口重叠（即 `新事件时间 < 现有窗口结束时间`），则触发窗口合并（Merge），窗口结束时间延长。
  2. **Watermark 驱动定版**：Watermark 决定了“什么时候不再等待合并”。只有当 `Watermark ≥ 窗口结束时间` 时，系统才认为该会话彻底结束，不再接受能合并的新数据（除非迟到）。

### 5.2 直观示例

**设定**：Session Gap = 5 分钟。

**Step 1: E1 (10:01) 到达**
系统创建窗口 **W1** `[10:01, 10:06)`。

```text
Event:  E1(10:01)
Window: [------- W1 (10:01 ~ 10:06) -------]
```

**Step 2: E2 (10:03) 到达**
E2 初始窗口为 `[10:03, 10:08)`。系统检测到它与 W1 重叠，**合并**为一个新窗口 **W_New** `[10:01, 10:08)`。

```text
Event:  E1(10:01)   E2(10:03)
Window: [----------- W_New (10:01 ~ 10:08) -----------]
```

**Step 3: Watermark 推进到 10:07**
（注：Watermark 的推进由后续到达的新数据驱动。假设此时收到了其他用户的数据或更晚的事件，使系统 Watermark 涨到了 10:07）
`Watermark (10:07) < W_New.End (10:08)`。窗口继续等待，不输出。

**Step 4: Watermark 推进到 10:08**
（后续事件继续到达，Watermark 最终达到 10:08）
`Watermark (10:08) ≥ W_New.End (10:08)`。
**触发点**！系统认为 10:08 之前不会再有填补该 Gap 的数据（在不考虑 Allowed Lateness 的情况下），输出 W_New 结果。

### 5.3 关键特性：连续活跃导致的“无限”延伸

**问题**：如果该用户持续活跃，每隔 1 分钟发送一个事件，窗口会怎样？

**答案**：窗口会**一直变大**，直到用户停止活跃超过 Gap 时间。

1. **机制**：只要新事件的 `EventTime` 在 `[当前窗口开始, 当前窗口结束)` 范围内（实际上是 `EventTime < 当前窗口结束`），它就会与现有窗口重叠并合并，导致窗口结束时间更新为 `NewEventTime + Gap`。
2. **现象**：若 Gap = 5 分钟，用户每 1 分钟操作一次，窗口结束时间会不断向后推迟（`+1m`）。Watermark 虽然在推进，但永远追不上不断后移的窗口结束时间。
3. **结果**：直到用户真正停止操作超过 5 分钟，窗口结束时间不再更新，Watermark 才能最终追上并触发关闭。
   - _工程提示_：对于超长会话（如 continuous viewing），生产中通常会配合 **PurgingTrigger** 或自定义 Trigger 定时输出中间结果，避免状态过大或数据延迟过高。

### 5.4 核心疑问：为什么其他用户的事件能推动当前用户的 Watermark？

**问题**：我在处理 User A 的窗口，为什么 User B 的事件到达会让 User A 的 Watermark 前进？

**答案**：因为 Watermark 通常是**流级别（Stream-level）**或**分区级别（Partition-level）**的全局时钟，而不是针对单个 Key 的。

1. **共享时钟机制**：

   - 想象一个教室（流），User A 和 User B 是坐在里面的学生。
   - Watermark 是挂在黑板上的**时钟**。
   - 只要有人（User B）进来并说“现在是 10:07 了”，老师就会把时钟拨到 10:07。
   - 此时，User A 抬头看时钟，也会发现现在是 10:07 了。

2. **设计的必要性**（避免“饿死”）：
   - 如果 Watermark 是按 Key 隔离的，那么一旦 User A 停止发送数据（下线了），User A 的 Watermark 就会永远停滞。
   - **后果**：User A 的窗口永远无法关闭，状态永远滞留在内存中，导致内存泄漏。
   - **利用全局进度**：通过复用整个数据流的进度（由活跃的 User B, C, D... 推动），系统可以判定“时间确实流逝了”，从而安全地关闭那些不再活跃用户的窗口。

## 6. 机制对比总结

| 特性                   | 滚动窗口 (Tumbling) | 滑动窗口 (Sliding)  | 会话窗口 (Session)      |
| :--------------------- | :------------------ | :------------------ | :---------------------- |
| **窗口边界**           | 固定，不重叠        | 固定，可重叠        | **动态**，由数据驱动    |
| **事件归属**           | 1 个窗口            | N 个窗口            | 初始 1 个，后合并       |
| **Watermark 触发条件** | `WM ≥ 固定结束时间` | `WM ≥ 固定结束时间` | `WM ≥ 动态结束时间`     |
| **交互复杂度**         | 低                  | 中                  | **高** (涉及合并与重算) |
