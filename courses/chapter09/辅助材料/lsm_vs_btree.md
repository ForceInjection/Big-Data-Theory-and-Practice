# LSM Tree vs B+ Tree：写优化与读优化的巅峰对决

## 阅读指南

在学习 HBase 的核心存储引擎 **LSM Tree (Log-Structured Merge Tree)** 之前，很多同学会有疑问：_“我需要先复习 B+ 树吗？”_

答案是：**非常有必要**。

LSM Tree 并不是凭空诞生的，它是为了解决 B+ 树在**大规模写入场景**下的物理瓶颈而设计的。如果不了解 B+ 树是如何工作的，你就无法真正理解 LSM Tree 到底“优化”了什么，以及它为此付出了什么代价。

这篇文章将通过对比这两种典型的存储引擎，带你理解分布式数据库设计的核心权衡：**Read-Optimized（读优化） vs Write-Optimized（写优化）**。

## 学习目标

- 理解 **随机 I/O** 与 **顺序 I/O** 的性能鸿沟（相差 100 倍以上）。
- 掌握 B+ 树的“原地更新”模式为何限制了写入吞吐。
- 掌握 LSM Tree 的“异地更新”（Append-only）模式如何极致提升写入性能。
- 理解 LSM Tree 的代价：**读放大（Read Amplification）**。

---

## 一、B+ 树：传统数据库的主流选择（读优化）

### 1. 核心思想：有序且原地更新

B+ 树是 MySQL、Oracle 等传统关系型数据库的默认选择。为了更好地理解它的局限性，我们需要先看看它的内部构造。

#### (1) B+ 树的解剖图

想象一棵高度平衡的“胖”树（通常只有 3-4 层），它的所有数据都存储在最底层的**叶子节点**中：

```text
       [ 根节点：索引 ]
      /             \
 [中间节点]       [中间节点]
  /    \          /    \
[叶子] [叶子] -> [叶子] [叶子]
 (数据) (数据)    (数据) (数据)
```

- **索引节点（根/中间）**：只存 Key 和指针，用来快速导航。
- **叶子节点**：存储完整的行数据（Row Data）。
- **链表连接**：所有叶子节点通过指针串成一个双向链表，这让“范围查询”（例如 `SELECT * FROM table WHERE id > 100`）变得非常快，只需要找到起点然后顺着链表走就行。

#### (2) 维护成本：分裂与平衡

B+ 树为了保证查询快（O(logN)），必须时刻保持树的**平衡**和**有序**。

**当插入新数据时：**

1. **理想情况**：目标叶子节点还有空位，直接把数据插进去，依然保持有序。
2. **糟糕情况（页分裂）**：目标叶子节点满了！
   - 需要把这个节点拆成两个。
   - 可能会导致父节点也满了，父节点也要拆。
   - 最坏情况会一直传播到根节点，导致整棵树的结构发生剧烈变化。

**更新方式**：**In-Place Update（原地更新）**。

- 当你要修改 ID=100 的记录时，数据库会找到它在磁盘上的具体位置（Page），然后直接修改那个位置的内容。

### 2. B+ 树的写入瓶颈：随机写（Random Write）

想象一下，系统正在高并发地向数据库插入数据：ID=1, ID=10000, ID=50, ID=999...

由于 B+ 树必须保持数据的**物理有序性**，这些数据会被分散插入到磁盘的不同 Page 中。这就导致了大量的 **随机磁盘 I/O**。

> **物理事实**：磁盘的磁头移动（Seek）是非常慢的。
>
> - 机械硬盘随机写：约 100-200 IOPS（每秒只能写几百次）。
> - 机械硬盘顺序写：约 100MB/s（相当于每秒几万次小写入）。

**结论**：当写入并发极高时，B+ 树会因为大量的磁盘寻道（Seek）而成为系统瓶颈。这就是为什么 MySQL 在海量写入场景下往往需要分库分表。

## 二、LSM Tree：大数据时代的挑战者（写优化）

### 1. 核心思想：顺序追加，延迟合并

LSM Tree（HBase, Cassandra, RocksDB 的核心）的设计初衷就是为了**避免随机写**。

它的逻辑非常直接且有效：
**写入时并不直接修改磁盘上的数据，而是先写入内存。**

1. **内存缓冲（MemStore）**：数据先写入内存，并在内存中进行排序（通常使用 SkipList）。
2. **顺序刷写（Flush）**：当内存满了，将数据**顺序写入**磁盘，生成一个新的、不可变的文件（SSTable）。
3. **日志保障（WAL）**：为了防止断电丢失数据，写入内存的同时会顺序追加一条日志到磁盘（Write Ahead Log）。

**关键特性：**

- **不做原地修改**：修改 ID=100 时，系统只是在新的文件中写入一条 "ID=100, NewValue"。
- **删除数据**：删除数据时，系统写入一条 "ID=100, Deleted" 的墓碑标记（Tombstone）。
- **全是顺序写**：无论是写 WAL 还是刷写 SSTable，磁盘磁头都是顺序移动，避免了随机寻道。

这种方式被称为 **Out-of-Place Update（异地更新）**。

### 2. 为什么写入快？

因为它把所有的“随机写”都转换成了**内存写 + 磁盘顺序写**。
顺序写的性能通常是随机写的 **100 倍以上**。这就是 HBase 能够承受每秒百万级写入的物理基础。

## 三、巅峰对决：没有免费的午餐

既然 LSM Tree 写入这么快，为什么 MySQL 不换用它？因为 LSM Tree 将**写入的开销转移到了读取阶段**。

### 1. 读取性能对比

- **B+ 树（读快）**：

  - 数据是严格有序且唯一的。
  - 查找 ID=100，利用索引只需极少的磁盘 IO（通常 1-3 次）就能直接找到最新值。
  - **Read Amplification（读放大）低**。

- **LSM Tree（读慢）**：
  - 数据分散在很多个文件中（MemStore, L0 SSTable, L1 SSTable...）。
  - ID=100 可能在历史文件中存在，随后被修改，最近又被标记删除。
  - 为了获取其最新状态，系统可能需要**检索多个文件**，并合并结果。
  - **Read Amplification（读放大）高**。

### 2. 怎么解决读慢的问题？

这正是我们在《从 40 亿整数到 HBase》中讨论的内容：

- **Bloom Filter**：快速判断某个文件里有没有这个 Key，没有就不读了。
- **Compaction（合并）**：后台不断地把小文件合并成大文件，清理掉旧数据和墓碑标记，恢复数据的有序性。

## 四、总结：如何选择？

| 维度         | B+ Tree (MySQL)        | LSM Tree (HBase)                      |
| :----------- | :--------------------- | :------------------------------------ |
| **设计目标** | **读多写少**           | **写多读少 / 海量写入**               |
| **写入模式** | 原地更新 (In-Place)    | 追加更新 (Out-of-Place)               |
| **磁盘 I/O** | 随机写 (慢)            | 顺序写 (极快)                         |
| **读取性能** | 极快且稳定 (O(logN))   | 较慢，依赖 Compaction 和 Bloom Filter |
| **适用场景** | 事务交易、强一致性查询 | 日志、监控、海量历史数据分析          |

**回答你最初的问题**：
是的，了解 B+ 树能让你深刻理解 **“Random vs Sequential”** 这对核心矛盾。
HBase 选择了 LSM Tree，并不是因为 LSM Tree 完美，而是因为在**大数据写入**这个特定战场上，**顺序写是唯一的生存法则**。
